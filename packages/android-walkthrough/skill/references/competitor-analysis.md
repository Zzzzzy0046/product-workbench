# 竞品分析工作流

当用户要完整 Android 竞品分析，而不只是截图留档时，读取本参考文件。

## 输出原则

把截图当作证据，不要把截图本身当成最终目标。最终目标是输出能支持产品决策的竞品分析，帮助用户判断：

- 竞品到底在做什么
- 它为什么这样做
- 变现和留存杠杆在哪里
- 哪些设计值得抄、哪些要避开、哪些可以差异化
- 对 Google Play、App Store、用户信任和转化有什么风险

默认使用中文输出。onboarding、paywall、subscription、IAP、banner、native ad、interstitial、retention、ASO、CTA、template、export 等产品术语可以保留英文。

## 工作流阶段

### 1. 分析输入

操作设备前，先推断或收集：

- 包名
- App 名称
- 目标品类
- 目标国家 / 商店地区，默认 US
- 多竞品时的竞品集合
- 用户期望的输出物：默认模块流程截图 PNG；按需快速小结、完整报告、Word docx、横向竞品对比表
- 用户只需要可见证据，还是也需要产品判断
- 分析深度：默认 `quick`；可选 `quick` / `standard` / `deep`

如果答案已经能从文件、包名、上下文、截图或 PDF 文档判断，不要重复问用户。

### 1b. 分析深度

默认不要用全量审计方式跑每一个竞品。以本轮问题和选定模块为范围；下列时长仅可作为事前预算，不是实测效率或完成承诺。实际耗时见 timings.jsonl。

`quick`，仅本轮所选模块：

- 适合批量看竞品、初筛、写 PDF 小结
- 不是“少看一点就结束”，而是“先抓高价值信息，低价值信息延后”
- 先观察首页/导航，按当前问题选择一个或几个核心任务；只采集这些路径的关键页面/状态，遇到 paywall/广告则记录，不为了补固定清单刻意触发
- 默认跳过：每个模板详情、每个底层设置、分享面板、法律页全文、重复列表项、非关键弹窗
- 输出：模块流程 PNG + 原始截图与结构留档；用户要判断时再给简短结论和待补路径

`standard`，主要模块闭环：

- 适合确认一个主要竞品
- 覆盖主 tab、核心任务完整闭环、主要高级功能、主要 paywall、广告触发、设置页
- 输出：模块流程 PNG 和证据；需要分析时给 product_summary.md，可选 Word，不重复维护两套页面结构

`deep`，用户明确要求的完整范围：

- 适合头部竞品或要做产品方案前的深挖
- 覆盖边缘菜单、错误态、权限拒绝、多个模板/内容样例、多轮广告触发、订阅挽留、评分弹窗、legal/trust 细节
- 输出：所选范围的完整证据、模块流程 PNG 和覆盖说明；完整竞品分析和 Word 仅按请求导出

如果用户没有明确要求“完整跑一遍 / 所有边缘菜单 / 全量截图”，默认使用 `quick`。

分析时可选择的高价值问题（不是 quick 每轮必跑清单；未观察到的写未知）：

- 首启路径：是否有 onboarding、语言选择、权限、启动广告、首启 paywall
- 首页结构：用户进来后看到什么，主 CTA 是什么，订阅入口在哪里
- 核心任务路径：核心任务能否从入口走到预览/结果/导出
- paywall 触发点：启动、主页入口、高级功能、模板、导出/保存是否触发
- 订阅价格和权益：价格、试用期、默认选中套餐、折扣、主要权益
- 广告体验：广告类型、触发时机、是否阻断主路径、是否外跳 Google Play
- 设置 / restore / legal 入口：不一定看全文，但入口要确认，特别是 restore purchase 和 privacy policy

quick 模式可以后置的信息：

- 每个模板详情
- 每个样式设置
- 每个边缘菜单
- 每种错误态
- 所有法律页正文
- 重复广告样式
- 多个相似表单字段
- 所有分享渠道
- 每个 tab 里的列表详情

需要标记缺口、考虑定向补采的情形：

- paywall 价格不清楚
- 导出 / 保存是否付费不清楚
- 广告触发频率异常高
- 核心功能路径没跑通
- 首页入口太多，无法判断主功能
- 涉及 AI、健康、金融、儿童、定位、UGC 等政策敏感品类
- 竞品明显是头部竞品，或用户指定它是重点竞品
- 截图和 UI dump 信息冲突
- 出现登录 / 订阅 / 权限阻断，导致核心价值无法验证

遇到这些情形不自动升级全 App deep，也不重跑已完成模块。记录 blocked/partial 及原因；仅当它影响本轮问题且授权/预算允许时，定向补必要页面。登录、订阅和权限阻断不能靠扩大扫描解决。

### 2. 商店页和市场层

可获得时，记录商店页证据：

- Google Play 标题、icon、开发者、品类、评分、评论数、下载量、年龄分级
- Contains ads / In-app purchases 标识
- 商店截图和首屏卖点
- ASO 定位：标题关键词、短描述信号、截图文案、AI / 工具 / 即时结果等包装
- 支持邮箱、隐私政策、Data safety、法律页面
- 用户提供的 Sensor Tower / 天眼 / 第三方链接

如果商店数据可能变化，且用户要求最新/当前信息，必须浏览或打开用户提供的页面确认。如果用户只提供静态截图或 PDF，就基于这些材料分析，并说明观察来源。

### 3. App 走查证据

先读 walkthrough.md，用 aw observe/act 采集；按选定范围从下列候选中采集：

- 启动页 / splash
- 语言 / 地区选择
- onboarding
- 权限弹窗
- app open ad / interstitial
- 首页和导航
- 每个可见 bottom tab 或主导航区
- 核心创建任务
- 编辑页 / 结果页 / 预览页
- 导出 / 分享 / 保存流程
- 设置 / 账号 / 法律页面 / restore purchase
- 评分弹窗
- 可触达的空状态 / 错误态 / 权限拒绝状态

用真实 UI 文案命名截图，不要把走查变成无边界乱点。

不按固定截图数量凑完成度。重复证明同一件事的画面可不再挂入地图；新状态或阻塞保留证据。业务模块依用户任务划分，UI XML 父子控件不能直接当产品架构。

### 4. 核心 JTBD 和功能矩阵

需要完整竞品判断时总结（仅有局部走查时只写已观察的部分）：

- 用户核心任务：这个 App 帮用户完成什么
- 核心路径：开始 -> 输入 -> 编辑/定制 -> 预览 -> 导出/分享/结果
- 主要模块和功能
- 免费能力和付费能力拆分
- AI 是核心价值，还是只是营销包装
- 模板 / 内容 / 结果是否真的有差异
- 用户看到价值前的摩擦点

对工具类 App，尤其是简历/CV、扫描、打印机、AirTag 类产品，不要只因为功能多就高估价值。要判断它是否真的缩短任务路径、提升结果质量，还是只是在包装一个同质化流程。

### 5. 商业化分析

本轮涉及商业化时，对实际看到的内容截图并总结；未出现的套餐/入口不补为事实：

- 变现模型：subscription、IAP、广告、hybrid、一次性购买
- paywall 触发点
- 订阅价格计划
- 免费试用期
- 默认选中的套餐
- 折扣 / 挽留 offer
- 关闭路径和 dark pattern 风险
- 被锁定的能力
- CTA 文案
- restore purchase 入口
- 导出 / 保存 / 查看结果是否被 gate

价格处理规则：

- 优先记录 US 商店或 App 内可见的美元价格。
- 如果设备显示本地货币，在证据中保留原币种，并在面向用户的小结里换算成近似美元。
- 如果用户要求只输出美元，只输出近似美元价格。
- 如果精确汇率会影响判断，必须查验当前汇率；否则使用近似值，不要制造虚假的精确感。

### 6. 广告分析

如果出现广告，读取 `ads.md` 并记录：

- 广告形式：app open、interstitial、banner、native、rewarded、playable、外部落地页
- 触发时机：启动、onboarding、语言选择、模板选择、导出、返回/关闭、重复点击
- 广告是否阻断核心流程
- 广告 CTA 是否导致 Google Play / 浏览器外跳
- 广告密度造成的可见摩擦；对信任或留存的影响仅作推断，不当成实测因果

不要点击广告里的 Install / Download / Open / Play now 等 CTA。

### 7. 留存、信任和政策风险

检查：

- 评分弹窗时机
- 通知权限请求时机
- 账号 / 登录要求
- 邮箱收集
- restore purchase 和订阅管理入口
- 隐私政策和条款入口
- 权限解释是否充分
- 敏感政策风险：AI、健康、金融、儿童、约会、UGC、定位、相机、联系人、SMS、Accessibility

面向 C 端出海产品时，如有相关风险，要单独指出 Google Play 风险。

### 8. 产品判断

默认使用这套判断结构：

- 用户是否清晰
- 痛点是否真实
- 核心路径是否足够短
- 用户首次看到价值的时间
- 付费墙是否卡在价值前还是价值后
- 订阅价格和权益是否匹配
- 广告是否破坏信任
- 留存机制是否自然
- 哪些设计值得抄
- 哪些设计不要抄
- 我们可以怎么差异化

要直接给判断，不要只描述页面。

## 交付物

### 结构与证据源

模块地图 `research-map.json` 维护页面/状态/跳转，原始 observations 保存图文证据，`app-map.md` 从地图派生。需要完整分析时再写 `product_summary.md` 并引用这些证据：

- 截图目录
- 逐页发现
- 截图引用
- 原始 paywall / 广告 / 评分证据
- 观察到的阻断点

### 决策报告

当用户要求完整竞品分析时，可直接在对话或一份报告中输出以下结构；不要默认再创建内容重复的 competitor_analysis.md 和 Word：

- 执行摘要
- App / 商店页基础信息
- 激活流程
- 核心功能矩阵
- 商业化和 paywall 地图
- 广告策略
- 留存 / 信任 / 政策观察
- UX 优势和摩擦
- 机会点和建议
- 多竞品横向对比，如果适用

### 可复制小结格式

当用户说“小结”、“写成类似这样”、“发出来不要 markdown”，或需要粘贴进 PDF / 文档时，使用下面的紧凑项目符号格式：

● 竞品广告/变现判断：说明广告强弱、订阅/IAP/广告组合，以及对体验的影响

● 竞品功能定位：说明核心工作流、主要功能模块、和对标竞品相比的差异；如果高级能力需要订阅后才可体验，要明确写出

● paywall 主要出现位置：列出启动流程、主页入口、设置页、高级功能、模板、导出、AI、评分、样式等入口

● 订阅出现时机
    ○ 启动流程中出现
    ○ 主页订阅入口
    ○ 设置页订阅入口
    ○ 使用高级功能进入
    ○ 导出/保存/分享时进入

● 订阅价格
    ○ 周：$X.XX（如有试用期，写明）
    ○ 月：$X.XX
    ○ 年：$X.XX（如有折扣价，写明）

只写有证据支持的内容。如果某个套餐或触发点没有观察到，就省略，或写“未观察到”。

### 多竞品横向对比

对比多个竞品时，使用这些维度：

- App / 包名
- 定位
- 核心流程
- 功能完整度
- AI 包装强度
- 模板 / 内容质量
- 广告强度
- paywall 时机
- 订阅价格
- 导出 / 保存 gate
- 留存 / 评分弹窗
- 信任 / 政策风险
- 值得抄的点
- 不要抄的点

面向用户的 C 端出海 App 工作，结尾必须给明确建议：

- 现在必须做
- 可以后置
- 不要做

## 质量标准

如果用户要求分析，不能只描述有哪些页面；将证据连接到产品判断。用户只要图片/模块地图时不强加这些报告章节：

- 对转化的影响
- 对留存的影响
- 对信任的影响
- Google Play / App Store 风险
- 产品差异化
- 变现适配度

如果证据不完整，要说明缺口，并区分事实和推断。
