# 工作台设计与扩展边界

## 当前目标

工作台不模拟大型团队的阶段流程，而是让小团队把现有资料快速转成新品分析、核心 PRD 和开发验收。

终极形态不是封闭的一套固定流程，而是“稳定工作台内核 + 可热插拔知识源与能力”。用户拿到工作台后，应能从界面连接自己的产品知识库，完成连通测试并立即用于任务检索；新增连接器、任务能力包、工具、校验器或导出器时，不应修改工作台主程序。

参考 [ai-pm-workflow](https://github.com/hy459229090-lang/ai-pm-workflow) 的上下文分层、任务资料路由、渐进建设和评审机制；不复制其业务代码。

## 默认结构

```text
浏览器：项目 / 背景 / 资料 / 任务 / 交付物 / 能力库
    ↓
app.py
    ├─ 项目与任务 → SQLite
    ├─ 文本与图片资料 → 原文件 + 可检索文本 + asset:// 图片引用
    ├─ 三个快速主任务 + 一个可选埋点任务 → capabilities/fast.json
    ├─ 上下文装配 → 项目 + 本轮要求 + 指定资料 + 精简知识
    ├─ 双索引检索 → 项目隔离 Hybrid 索引 + Product KB 全局只读索引 + 关键词回退
    ├─ 执行器 → Codex CLI
    ├─ 竞品评论 → 桌面 scraper 子进程 → 规范化 CSV → 项目资料
    ├─ 导出 → Markdown 渲染器 → Word / PDF / Excel / CSV
    ├─ 项目包 → manifest + JSON + uploads/runs/scrapes ZIP → UUID 重映射导入
    └─ 编辑、批注、版本与评审 → 内容块定位批注、Markdown 正文、不可变版本链、草稿、确认与轻量质量校验
```

交付物的当前正文保存在 `jobs.output` 与项目 `documents` 中；每次生成、导入、手工编辑或恢复都会追加到 `job_versions`。恢复历史版本采用“复制为新版本”，不改写旧记录。编辑已确认正文时删除旧评审结论，并把项目文档降回待评审草稿，只有重新确认后才会进入后续检索。

定位批注保存在 `document_comments`，通过 `job_id + version + block_id + quote` 绑定到某个版本的标题、段落、引用、表格或代码块。`block_id` 只在该版本内稳定，`quote` 用于系统元数据迁移后的重新定位。批注修订任务只读取当前版本的待处理批注，并把位置、原文摘录、动作和意见放入任务包；批注数据不写入产品正文。新版生成成功后，本次实际使用的批注自动关闭。

任务通过 `workflow_mode` 保存生成时模式，通过 `parent_job_id + revision_number + revision_reason + source_version` 保存修订链。失败、取消和重启中断都可以恢复为待执行；归档只改变列表可见性，不删除任务证据。

评审确认有三层保护：当前版本不能有待处理批注；正文中的每个 `[Sx]` 必须存在于该任务来源快照；F3 的 `Conditional` 结果必须按模式闭环。快速模式要求在同一 F3 清单修改与复测为通过，完整模式允许登记带 Owner 和截止时间的条件。

引用已有交付物时，来源装配会把其底层来源展开、去重和重新编号，避免嵌套文档把旧的 `[Sx]` 带入新任务。完成和手工编辑阶段再次进行引用完整性校验。

项目删除采用二次确认和本地回收机制。服务端校验完整项目名并拒绝删除运行中项目；删除 SQLite 当前记录前，将项目、批注及其他关联表导出为 JSON，并把 uploads 与 runs 移入项目专属回收目录，同时清理项目向量和 manifest 条目。回收目录不参与工作台检索，可从界面恢复；恢复后在下次检索时重建项目索引。永久删除再次校验完整项目名、受限目录并执行索引清理。

项目索引只同步当前项目的上传资料和已确认交付物。向量 source ID 带项目命名空间，返回工作台时再恢复为原文档 ID；组合检索先保留项目证据，再用全局 active 方法、模板和案例补足。浏览器和任务快照保留可核对的来源原文，但剥离向量 ID、内部得分和索引治理字段。Hybrid 初始化或查询失败时自动使用原有关键词检索，不阻断任务准备。

快速模式不显示条件闭环，不生成风险、假设验证、技术 Spike 或 Gate。旧数据结构保留供完整模式和历史项目兼容。

完整埋点是快速模式中的可选分支，不改变默认的 F1 → F2 → F3 主链。选择后，当前会话可用 Lanhu MCP 只读读取用户有权限访问的原型页面，再把脱敏页面、状态和交互文字通过 `/api/lanhu/snapshot` 导入项目资料；工作台不保存 Cookie、Token 或浏览器会话。没有蓝湖时也可以使用截图、PRD 或交互说明。埋点任务消费已确认的 F2 与这些证据，输出中文 Markdown 事件方案；事件 ID、参数名和枚举值保留英文。交付物生成、导入、编辑和恢复后都会执行 F1/F2/埋点/F3 的轻量确定性检查，只有硬错误阻止确认。

## 控制文档长度

- 每个快速任务在能力定义中配置 `max_chars`；
- F1 的控制目标是保留 Heart Rate 式完整产品故事，建议 12,000–16,000 字；它写模块级方案，F2 再写页面级规则；
- Prompt 要求只写本交付物新增内容，不复述上游；
- 工作流审计单独存在，不进入产品文档；
- 原始附件进入资料索引和结论引用，不复制完整原文；
- F3 在同一份文档中更新计划与实测，不再拆分。

## 扩展点

任务继续通过 `capabilities/*.json` 和 Markdown 模板扩展。工具扩展必须实现后端适配器；仅登记名称不等于可执行。

当前这套机制只是插件化雏形：任务定义可以配置，但全局知识目录、检索实现、工具注册、校验器和导出器仍与主程序耦合。下一阶段先增加插件运行时与 Knowledge Gateway，再把现有能力逐步迁移为标准插件。首批通用知识入口为本地目录、Product KB MCP 和可配置工具映射的通用 MCP；特殊企业知识库通过独立连接器扩展。

插件统一分为五类：`knowledge-source`、`capability`、`tool`、`validator` 和 `exporter`。所有插件都声明 manifest、版本、配置结构、权限、入口和健康状态。默认只读；凭证保存在本机私密配置中，不进入项目包、日志或 Git。

知识源连接器统一提供 `health`、`search`、`get`、`trace`，并可选提供 `sync`、增量游标和 `writeback`。连接器配置与凭证分离，支持实时查询 `federated` 和本地缓存索引 `indexed` 两种模式。现在只实现本地目录、Product KB MCP 和通用 MCP；Notion、钉钉、飞书、Confluence 等先预留适配器接口和配置 Schema，后续新增适配器即可接入，不改检索服务和任务逻辑。

桌面评论采集器和 Word/PDF/Excel/CSV 导出已经作为本地适配器接入；后续可继续增加检索过滤、知识候选和更多任务包。账号、多 Agent、自动全局知识发布和商店发布不在当前范围。
