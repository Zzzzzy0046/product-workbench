# 公司快速交付 PRD 使用说明（v2.0）

> 最新使用入口：[PRD文档体系-v2.0.md](./PRD文档体系-v2.0.md)

现有需求不再统一套用一份“大而全”的 PRD。请先判断需求属于新品立项、新品交付、版本迭代还是低风险小改动，再选择对应模板。

## 模板选择

- 新品还在判断值不值得做：使用《01-新品产品定义与立项方案模板》。
- 新品已经立项，需要完整首版交付：使用《02-新品 PRD 模板》。
- 已有产品新增或修改功能：使用《03-迭代 PRD 模板》。
- 单点且低风险的小改动：使用《04-快速需求单模板》。

旧版《公司通用 PRD 模板 v1.0》只用于查看历史文档，不再作为新需求的默认入口。

## 定位

这是一套小团队快速交付文档体系，不是大公司的流程审批文档。统一的是判断方式和关键检查项，不要求所有需求写得很长。

建议篇幅：

- 新品产品定义与立项方案：5–10 页，详细数据可放附件。
- 新品 PRD：按 MVP 页面数展开，不重复粘贴完整市场研究。
- 迭代 PRD：通常 3–8 页，只展开变化和影响范围。
- 快速需求单：通常 1–2 页。

## 分工

- 产品：主写 PRD，决定目标、范围、优先级、流程、业务规则和验收结果，并对最终版本负责。
- Agent：在产品初稿基础上整理表达、检查遗漏和发现冲突；不从空白输入替产品生成正式 PRD，也不能确认关键规则。
- 设计：确认页面结构、状态、交互和美术交付范围。
- 研发：确认系统行为、权限、技术依赖和降级方案。
- 测试：确认状态、异常和验收标准可执行。

## 产品经理必须亲自写的内容

- 为什么做：目标用户、使用场景、核心问题和产品目标。
- 做什么：本期必须做、可以后置、明确不做和功能优先级。
- 怎么走：首次使用、核心路径、失败、取消和恢复。
- 页面做什么：每个页面的目的、入口、核心任务和成功结果。
- 业务怎么判定：保存、删除、成功、失败、付费和数据变化规则。
- 什么算完成：P0 需求的可验证验收结果。

以上内容不能由竞品截图、原型模板或 Agent 常识自动推导成正式结论。

## 设计、研发和测试协作补充的内容

- 设计：信息层级、控件方案、状态表达和美术出图范围。
- 研发：准确权限名称、SDK 行为、技术阈值、数据结构、兼容性和降级方案。
- 测试：完整测试条件、边界组合、回归范围和测试数据。

产品经理仍需确认这些补充是否改变产品体验和需求范围。

## 正常使用方式

### 新品

1. 产品经理先填写《01-新品产品定义与立项方案》，提交 `Go / Hold / No-Go` 评审。
2. 只有结论为 Go，才把批准的用户、定位、MVP 范围、产品框架和核心流程带入《02-新品 PRD》。
3. 先完成新品 PRD 的产品结构、流程和页面清单，再展开每个 P0 页面的详细需求。
4. 页面画面确认后，补齐与页面模块一一对应的需求说明、业务规则和验收标准。
5. 设计、研发和测试补充专业结论，产品经理确认是否改变用户体验或范围。

### 迭代

1. 产品经理填写《03-迭代 PRD》的当前问题、证据、目标和 Before / After。
2. 列全受影响的页面、流程、数据、权限、商业化和既有用户，不重新复制整个产品说明。
3. 只展开变化的详细需求，同时明确哪些内容保持不变。
4. 产品、研发和测试共同确认兼容、迁移、回归、灰度和回滚范围。

### 小改动

1. 确认改动是单点、低风险且不影响核心流程。
2. 使用《04-快速需求单》写清 Before / After、范围和验收。
3. 一旦发现跨页面、数据、权限、支付、广告或隐私影响，立即升级为《03-迭代 PRD》。

## 给 Agent 的正确调用方式

```text
这是我按照《[新品产品定义与立项方案 / 新品 PRD / 迭代 PRD / 快速需求单]》写的初稿。

请不要替我扩充产品范围，也不要直接改写我的产品决策。

请帮我：
1. 先检查我选择的文档类型是否正确；若不正确，说明原因。
2. 检查目标、范围、功能、流程和页面是否一致。
3. 新品 PRD 检查产品基线是否完整；迭代 PRD 重点检查 Before / After、影响范围、兼容和回归。
4. 找出遗漏的成功、失败、取消、返回和恢复路径。
5. 找出没有来源的产品假设，以及被竞品截图带入的业务规则。
6. 检查权限、数据、商业化、隐私和平台政策边界。
7. 将问题分成“必须现在确认”和“可以后置”。
8. 优化结构和文字表达，但把涉及产品决策的修改列为建议，等我确认。
9. 输出检查结果和建议修改清单，不直接生成原型。
```

Agent 检查后，产品经理可以继续发送：

```text
下面是我对问题的决定：
1. ……
2. ……

请据此更新同一份 PRD：
- 只修改对应章节；
- 保留未解决问题；
- 不改动无关产品规则；
- 在变更记录中记录本次修改。
```

## 进入原型的最低条件

- 目标用户和核心问题明确。
- 本期做与不做的范围明确。
- 核心流程与页面清单明确。
- 影响页面结构的关键问题已解决。
- 权限、数据和商业化已确认或明确不涉及。
- P0 功能有可验证的成功结果。

满足以上条件后，原型 Skill 才读取 PRD，生成页面画面；页面确认后，再根据同一份 PRD 生成右侧需求说明和 Axure 内容。
