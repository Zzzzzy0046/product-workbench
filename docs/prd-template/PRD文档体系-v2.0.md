# 公司产品需求文档体系 v2.0

> 目标：让团队先选对文档，再开始写内容。不是所有需求都叫 PRD，也不是所有 PRD 都使用同一套结构。

## 一、四类文档

| 编号 | 文档 | 解决的问题 | 适用场景 | 主要结论 |
|---|---|---|---|---|
| 01 | 新品产品定义与立项方案 | 值不值得做、做成什么产品 | 新品、独立产品方向、重大业务探索 | `Go / Hold / No-Go` |
| 02 | 新品 PRD | 第一版产品具体怎么做 | 已确认立项，需要设计、研发和测试交付完整首版 | 建立产品 v1.0 基线 |
| 03 | 迭代 PRD | 现有产品从什么变成什么 | 新功能、流程调整、商业化改造、体验优化 | 描述变化、影响和回归范围 |
| 04 | 快速需求单 | 一个低风险小改动如何交付 | 文案、配置、单点样式、单页面轻逻辑、Bugfix | 快速修改并验收 |

## 二、选择规则

```text
这是一个还未正式立项的新产品方向吗？
├─ 是 → 先写 01 新品产品定义与立项方案
│        ├─ Hold / No-Go → 不进入 PRD
│        └─ Go → 写 02 新品 PRD
└─ 否，已有线上产品或既有版本
         ├─ 跨页面、跨模块、改流程/数据/商业化 → 写 03 迭代 PRD
         └─ 单点、低风险、无复杂状态与数据迁移 → 写 04 快速需求单
```

以下任一项成立，就不要使用快速需求单：

- 新增或改变核心用户流程。
- 涉及登录、账号、支付、订阅、广告、权限、隐私或敏感数据。
- 涉及数据结构、历史数据迁移、云同步或跨端一致性。
- 影响两个及以上页面或多个模块。
- 失败后会阻断核心任务，或者需要完整降级、回滚方案。

## 三、新品 PRD 与迭代 PRD 的本质区别

| 维度 | 新品 PRD | 迭代 PRD |
|---|---|---|
| 起点 | 目前没有产品基线 | 已有线上或已确认版本 |
| 核心写法 | 定义完整产品如何成立 | 定义现状如何变化 |
| 必写内容 | 产品边界、信息架构、完整核心流程、页面全集、全局规则 | 现状证据、变更前后、影响范围、兼容与回归 |
| 页面范围 | 覆盖 MVP 全部必要页面 | 只展开受影响页面，并列出未改部分 |
| 规则范围 | 建立第一套正式规则 | 明确新增、修改、删除和保持不变的规则 |
| 验收重点 | 产品能否从头到尾完成核心任务 | 变化是否生效，既有能力是否未被破坏 |
| 研究内容 | 从已通过的立项方案引用结论，不重复整份市场研究 | 通常不写行业大盘，只写与本次变化直接相关的证据 |

## 四、标准工作流

### 新品

```text
产品想法 / 产品功能框架 / 竞品截图 / 市场与用户证据
→ 01 新品产品定义与立项方案
→ 立项评审
→ 02 新品 PRD
→ 页面清单
→ 低保真原型
→ 需求说明与验收
→ 设计 / 研发 / 测试
```

### 迭代

```text
线上问题 / 用户反馈 / 数据 / 业务目标
→ 判断改动规模和风险
→ 03 迭代 PRD 或 04 快速需求单
→ 受影响页面原型
→ 评审与开发
→ 回归验证
```

## 五、文件命名

- 新品立项：`产品名-新品产品定义与立项方案-v0.1.md`
- 新品 PRD：`PRD-产品名-v1.0.md`
- 迭代 PRD：`PRD-产品名-功能名-v版本号.md`
- 快速需求：`REQ-产品名-改动名-日期.md`
