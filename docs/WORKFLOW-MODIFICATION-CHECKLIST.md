# 小型出海 App 工作流修改清单

> **历史版本说明：** 本文记录 V0.2 的改造过程，不是当前操作手册。当前 V0.3 已进一步收缩为 `F1 新品需求分析 → F2 核心 PRD → F3 开发验收清单`，不再默认要求条件闭环、风险清单、技术 Spike、用户访谈或 F1–F6 全套交付物。请以 `WORKFLOW-USER-MANUAL.md` 为准。

> 这是基于 GBA Emulator 全流程实际运行后的修改清单。V0.2 已完成核心流程调整；原始检查项继续保留，便于验收和安排扩展能力。

## P0：必须修改，否则仍然偏重或无法闭环

### P0-01 增加 Fast Iteration Path

- [ ] 在工作流入口增加“快速迭代模式”，默认适用于小团队和已决定要做的品类。
- [ ] 输入不再默认经过完整机会分析；机会门改为可选记录，不作为阻断。
- [ ] 默认交付顺序改为：输入卡 → 快速定义卡 → Spike/竞品评论并行 → 核心 PRD → 最小验收。
- [ ] 完整 T1–T4 保留为“完整研究模式”，由用户主动选择。
- [ ] 两种模式的输出必须标明模式名，避免同事误把快速版当完整市场结论。

### P0-02 把“条件”变成可关闭的任务对象

- [ ] 每一个硬条件必须有：`condition_id`、Owner、截止时间、状态、证据链接、复核日期。
- [ ] 状态至少包括：`未开始 / 进行中 / 待证据 / 已关闭 / 豁免`。
- [ ] `Conditional Go` 没有 Owner 或截止时间时，禁止作为最终状态保存。
- [ ] 每个条件必须声明：阻塞开发、阻塞内部测试，还是只阻塞外部发布。
- [ ] 工作台增加“条件关闭面板”，不要只把条件埋在 Markdown 末尾。

### P0-03 允许并行，不强制所有文档串行接受

- [ ] 下游任务允许读取 `draft` 文档，但必须显示“基于草稿，结论可能变化”的警告。
- [ ] 只有进入内部测试/外部发布前，才要求上游关键文档为 `accepted`。
- [ ] T1、评论证据、技术 Spike、低保真页面和 QA 计划允许并行。
- [ ] 引用资料增加版本号和更新时间，避免草稿更新后无法识别下游依据。

### P0-04 将 T4 拆成两个交付物

- [ ] `T4-Plan`：开发前定义最小事件、核心 QA、门槛和证据要求。
- [ ] `T4-Run`：真实构建后的设备、版本、录像、日志、实际结果、缺陷和复测结论。
- [ ] “计划中”不能使用“通过”；必须有实际证据才可标记 `Accepted`。
- [ ] T4-Run 必须支持导入测试包、日志、截图或录像索引，而不是只填文字。

### P0-05 增加团队和时间输入

- [ ] 项目输入卡增加：Android 研发人数、设计投入、QA 投入、合规支持、可用设备、预期验证周期。
- [ ] 默认目标按 1–2 周验证周期生成，不默认生成数月版本路线图。
- [ ] 每个交付物显示预估耗时和最小参与角色。
- [ ] 缺少角色时，输出“谁不能直接执行”的提示。

## P1：强烈建议修改，能明显提高日常使用效率

### P1-01 将竞品工作改为 Delta Pack

- [ ] 默认只选 3–5 个直接竞品，不生成大而全的竞品长卡。
- [ ] 每个竞品只保留：核心任务、第一次价值、关键痛点、可借鉴机制、只可参考的体验、明确不复制的资产/文案、原始评论证据。
- [ ] 新增统一表格：`借鉴什么 / 为什么借鉴 / 我们如何不同 / 不复制什么 / 证据链接`。
- [ ] 竞品评论采集器导出的 CSV 作为标准输入，不再只是手工导入的旁路工具。
- [ ] 评论分析先输出“需求信号和反方证据”，再决定是否进入 PRD。

### P1-02 将深度研究改为按需展开

- [ ] 默认不要求五区域市场表；先指定一个初始市场或标记“市场尚未决定”。
- [ ] 默认不要求 TAM/SAM/SOM；只有涉及融资、正式立项或资源争夺时才展开。
- [ ] 用户研究默认使用小样本任务测试/评论证据，10–15 人访谈作为可选增强项，不作为技术启动前置条件。
- [ ] 竞品价格、下载量、评分必须带 `observed_at`、来源和事实有效期。

### P1-03 T3 改成“核心页面 + 异常矩阵”

- [ ] 快速模式默认只做核心 4 页面：入口/导入、首页/最近、核心会话、保存/恢复。
- [ ] 设置、帮助、完整异常详情页按需要展开，不作为第一轮必做页面。
- [ ] 异常优先用统一矩阵表达：触发、用户看到什么、可执行动作、恢复结果、验收 ID。
- [ ] 技术 Spike 未冻结的字段必须显示“待 Spike”，不能写成确定产品规则。

### P1-04 建立交付物之间的机器可追踪映射

- [ ] T2 Spike → T3 页面规则 → T4 QA 用例必须有稳定 ID。
- [ ] 每个硬条件至少映射一个页面、一个 QA 用例和一条证据要求。
- [ ] 每个页面状态至少映射一个测试用例；无映射时给出遗漏警告。
- [ ] 页面交接清单区分：可给设计、可给研发、待技术确认、待用户验证。

### P1-05 将最小埋点设为默认

- [ ] 默认只生成 5–8 个回答核心闭环的事件。
- [ ] 事件字段必须区分“可立即定义”和“必须等待 Spike 冻结”。
- [ ] 详细按钮点击、商业化、广告、投放归因、跨设备和高级性能事件默认后置。
- [ ] 事件验收必须检查去重、失败/取消、数据最小化和实际日志，不只检查 ID。

### P1-06 增加小团队内部测试门槛

- [ ] 门槛分为：硬阻塞、内部测试前必须修复、可以后置。
- [ ] 内部测试不要求完整商店发布、投放、ASO、iOS 或商业化结论。
- [ ] 允许“只在 1 类设备跑通核心闭环”的早期技术结论，但必须标记支持范围，不得宣称广泛兼容。
- [ ] “可进入小规模开发”与“V0 已通过”必须是两个不同状态。

### P1-07 统一证据规则

- [ ] 所有关键结论标明：事实、推断、假设、决策、风险、待验证。
- [ ] 历史目标、规划阈值和实测结果必须使用不同字段。
- [ ] 竞品、价格、政策和商店数据必须保存来源、观察日期和快照版本。
- [ ] 真实验收必须记录构建版本、设备、操作步骤、实际结果、日志/截图/录像和复测版本。

### P1-08 同步技能、模板和工作台

- [ ] 检查 `overseas-consumer-app-lifecycle` 技能中仍然保留的完整新品/机会门默认描述。
- [ ] 与当前工作台的“品类已决定、机会门可跳过、Android-first、中文交付”规则统一。
- [ ] 检查 `overseas-consumer-app-workflow`、T1–T4 模板和工作台 task router 是否存在相互矛盾的 Gate、平台和输出要求。
- [ ] 统一“投放和商店发布默认不进入本流程”的范围边界。

## P2：可后置，但应保留扩展位

- [ ] 完整用户画像、长期留存模型和商业化方案。
- [ ] iOS、跨平台、多系统、云同步、账号体系。
- [ ] 完整地区策略、多语言、定价和收入预测。
- [ ] 完整按钮级埋点、性能指标、广告和投放归因。
- [ ] 真实原型文件自动生成与 Axure/Figma/Lanhu 的连接。
- [ ] Hybrid RAG、结构化实体检索和资料自动版本治理。

## 立即可以执行的修改顺序

1. 先实现 P0-01：快速迭代模式和最小输入卡。
2. 同时实现 P0-02：条件 Owner/截止时间/证据闭环。
3. 再实现 P0-03：允许草稿并行，解除 T1→T2→T3→T4 的绝对串行。
4. 将现有 T4 拆成 Plan/Run，避免把验收计划当成已通过结果。
5. 增加 P1-01 竞品 Delta Pack，并把桌面竞品评论采集器接到该环节。
6. 最后同步技能文件、模板和工作台规则，消除默认行为漂移。

## 修改完成后的验收标准

- [ ] 输入一个已经决定要做的新品，1 天内能得到快速定义卡和 Spike 清单。
- [ ] 竞品评论 CSV 能直接进入需求信号和 Delta Pack，而不是另开一套流程。
- [ ] 技术 Spike、低保真 PRD 和 QA 计划可以并行推进。
- [ ] 任意 Conditional 条件都能查到 Owner、截止时间和证据。
- [ ] 小团队可以只跑核心 4 页面和最小 T4，不被 iOS、商业化、投放和商店发布字段拖慢。
- [ ] 真实构建通过前，系统不会把计划文档标为已验收。
- [ ] 完整研究仍可按需展开，不丢失后续扩展能力。
