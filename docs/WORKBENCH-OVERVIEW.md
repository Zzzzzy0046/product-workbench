# 本地产品工作台介绍

版本：V0.9  
适用团队：小型、快速迭代的出海 C 端 App 团队  
默认语言：中文  
运行方式：本机浏览器 + 本地 Python 服务

## 1. 这是什么

本地产品工作台是一套面向产品经理的轻量交付系统。它把一个已经决定要做的新品，连同竞品评论、研究资料、截图、政策来源和技术记录，逐步整理成可以交给研发和设计继续使用的产品文档。

它不是市场机会筛选器，也不是大型公司的立项审批系统。工作台默认接受“这个品类就是要做”的前提，重点解决三个问题：

1. 资料分散，结论无法追溯；
2. 新品分析、PRD、验收清单之间容易断层；
3. 文档生成后难以协作修改、评审和保留版本。

默认工作流如下：

```text
项目背景与资料
      ↓
F1 新品需求分析
      ↓
F2 核心 PRD
      ├─ F3 开发验收清单
      └─ 完整埋点方案（按需启用）
```

## 2. 适用场景

工作台特别适合以下工作：

- 基于竞品快速开发同类 App；
- Android-first 的海外消费类产品；
- 产品经理需要在一到两周内完成方向、核心页面和开发交付；
- 资料来自多个来源，需要保留证据和引用；
- 交付物需要反复编辑、批注、修订和确认；
- 某个项目的埋点事件较多，需要从 PRD、截图或蓝湖原型整理完整事件表。

不适合把它当作以下系统：

- 多租户 SaaS 或多人实时协同平台；
- 统一管理公司所有账号和密钥的后台；
- 自动替代产品经理做最终决策的系统；
- 自动发布到 Google Play、App Store 或其他外部平台的流水线。

## 3. 核心技术能力

### 3.1 本地运行架构

```text
浏览器界面
   ↓ HTTP
本地 Python Workbench 服务
   ├─ SQLite：项目、资料、任务、版本、评审和批注
   ├─ uploads：原始文件和截图
   ├─ runs：任务包、执行记录和交付物版本
   ├─ Hybrid RAG：项目索引 + Product KB 全局索引
   └─ Codex CLI：执行中文文档生成
```

工作台使用本机 `127.0.0.1` 服务，不要求把项目资料上传到一个独立的工作台云端。生成任务开始时，选中的任务包和图片会发送给模型服务；未被任务引用的资料不会自动发送。

### 3.2 项目隔离与 RAG

工作台的检索分为两层：

- 项目层：当前项目上传的资料和已确认交付物；
- 知识层：全局只读 Product KB 中的方法、模板和历史案例。

项目资料优先，方法知识只用于补充结构和工作方法。草稿不会自动进入下游检索，只有用户显式勾选时才会作为带警告的输入。

Hybrid 检索不可用时，会自动回退到关键词检索，不会阻断任务准备和文档生成。生成结果保留 `[S1]` 等来源编号，保存和确认前会校验引用是否真实存在。

### 3.3 多格式资料解析

支持导入：

- Markdown、TXT、CSV、JSON；
- 文本型 PDF；
- DOCX；
- PNG、JPG、JPEG、WEBP 截图。

单份资料最大 12 MB。文本资料会被解析并切片，图片会保留原文件，并在生成任务中作为视觉输入。扫描 PDF 需要先做 OCR。

### 3.4 中文交付物生成

工作台默认要求最终文档使用中文，适合直接交给中文产品、研发和设计团队阅读。

与产品实现有关的英文内容可以保留，例如：

- 英文 UI copy；
- event ID；
- 参数名和枚举值；
- SDK 名称；
- 技术接口名。

生成任务使用项目背景、当前要求、指定资料和对应模板组装任务包，再由本机 Codex CLI 执行。每个任务都会保存输入快照，保证之后能够复盘“当时依据了什么”。

### 3.5 编辑、版本与定位批注

交付物不是一次性生成后就结束，而是可以继续处理：

- 直接编辑 Markdown 正文；
- 对标题、段落、表格和引用添加定位批注；
- 指定批注动作：新增、修改、删除、压缩、保留；
- 按当前版本待处理批注生成修订版；
- 查看版本链；
- 恢复历史版本，但恢复会创建新版本，不覆盖旧版本；
- 已确认文档发生编辑后自动回到待评审状态。

批注绑定具体文档版本，不会因为后续编辑而错误作用到新版本。修订时，未被批注的内容原则上保持原意和信息量。

### 3.6 任务恢复与项目回收站

任务在待执行、排队或生成过程中可以取消。取消、失败和服务重启中断不会删除任务包和输入快照，可以恢复为待执行。

项目删除采用二次确认：

1. 输入完整项目名称；
2. 项目移入本地回收站；
3. 项目资料、任务包、交付物、版本和批注会保存为恢复快照；
4. 需要时可以恢复；
5. 永久删除需要再次确认，且不可恢复。

## 4. 默认工作流

### F1 新品需求分析

F1 沿用 Heart Rate 新品分析的产品故事结构，主要回答：

- 行业和市场是什么；
- 用户是谁、有什么具体场景；
- 竞品有哪些差异；
- 产品应该如何定位；
- V0 先做什么、不做什么；
- 功能框架和核心模块如何组织；
- 主要流程是什么；
- 商业化方向是否自然。

F1 不单独生成平台、权限、数据或政策章节，也不要求用户访谈、假设验证、风险清单或技术 Spike。默认上限为 16,000 个中文字符。

### F2 核心 PRD

F2 只写本轮真正要开发的页面或功能，重点包括：

- 页面结构；
- 交互动作；
- 业务规则；
- Loading、Empty、Error 等状态；
- 失败、取消、超时和恢复；
- 必要的英文 UI copy；
- 可交给研发执行的验收标准。

默认聚焦 3–5 个页面或核心功能，上限为 8,000 个中文字符。

### F3 开发验收清单

F3 采用同一份清单记录开发前后的信息：

- 开发前预期；
- 开发后实测；
- 日志、截图和构建信息；
- 发现的问题；
- 修改记录；
- 复测结果。

默认上限为 5,000 个中文字符。F3 不要求重新创建另一份验收报告。

### 完整埋点方案（可选）

当事件数量较多，或者需要给研发一份完整事件表时，可以在 F2 后启用该任务。输入可以包括：

- 已确认的 F2；
- 蓝湖原型快照；
- 页面截图；
- 交互说明；
- 已有埋点资料。

方案覆盖页面展示、普通点击、选择、业务最终结果、权限、失败、取消、超时、重试、漏斗、隐私和 F3 验收映射。

规则是：

- 文档说明使用中文；
- event ID、参数名和枚举值使用英文；
- 只记录能够回答产品问题的事件；
- 不把每个按钮机械地拆成事件；
- 异步业务使用最终结果事件，不用点击事件冒充成功；
- 不记录 Cookie、Token、原始用户内容、精确位置、设备地址或可识别的蓝牙广播标识；
- 原型里没有的页面和状态不凭空新增。

当前交付物是可编辑中文 Markdown，单份上限为 20,000 个中文字符。

## 5. 蓝湖 MCP 能力

工作台支持在「能力与工具」页面配置 Lanhu MCP：

- 自动检测本机 `~/.codex/config.toml`；
- 支持指定其他配置文件路径；
- 检测 `npx` 和 MCP 包；
- 检测是否存在认证环境变量；
- 未安装时提供 Node.js / `npx` 安装指引；
- 不显示或保存 Cookie、Token 等认证值。

当前架构把蓝湖分成两部分：

```text
Lanhu MCP 客户端
  → 读取页面和状态
  → 生成脱敏快照
  → /api/lanhu/snapshot
  → 工作台资料与检索
```

配置检测入口已经在工作台中提供；实际页面读取仍由 MCP 客户端触发，工作台不会自动猜测蓝湖页面内容。没有 Lanhu MCP 时，可以继续上传截图、PRD 或手动快照，不影响主工作流。

## 6. 实际使用方法

### 启动

在仓库根目录运行：

```powershell
.venv\Scripts\python.exe workbench\app.py
```

然后打开：

```text
http://127.0.0.1:8765
```

也可以运行：

```powershell
workbench\start.ps1
```

生成任务需要本机已登录 Codex CLI，并且需要联网。

### 创建项目

1. 点击新建项目；
2. 填写项目名称和产品简介；
3. 选择「快速迭代」；
4. 目标平台可从 Android、iOS、双平台中选择，也可以暂不指定；团队和验证周期不再作为项目输入项；
5. 保存项目背景。

新品默认就是要做，不需要先通过机会门。

### 导入资料

进入「资料与检索」：

1. 上传竞品评论 CSV、研究资料、截图、政策来源或技术日志；
2. 在搜索框检索项目资料和方法知识；
3. 确认资料是否被正确解析；
4. 在准备任务时勾选真正要写进当前文档的资料。

资料会保存在本机项目目录中，不会自动进入 Git。

### 配置 Lanhu MCP

进入「能力与工具」：

1. 找到 Lanhu MCP 卡片；
2. 点击「配置 / 重新检测」；
3. 默认使用本机 Codex 配置，也可以指定配置路径；
4. 没有 Node.js 时，先安装 Node.js；
5. 没有认证时，配置自己的蓝湖权限；
6. 配置检测通过后，再使用蓝湖读取和快照导入。

每个同事都应该使用自己的蓝湖权限，不要复制其他人的 Cookie。

### 生成交付物

进入「任务」：

1. 选择 F1、F2 或 F3；
2. 埋点较多时，选择「完整埋点方案（可选）」；
3. 填写本轮重点；
4. 勾选指定资料；
5. 生成任务包；
6. 检查输入依据；
7. 点击开始生成；
8. 在交付物页评审、编辑或添加批注。

### 确认与下游使用

交付物生成后默认是“待评审”状态。确认前需要满足：

- 来源编号可追溯；
- 没有当前版本的待处理批注；
- F3 的验收结果满足快速模式规则；
- 文档内容已经由产品或研发检查。

确认后的交付物才会自动进入当前项目后续检索。

## 7. 工作台的主要特点

### 轻量

默认只有 F1、F2、F3 三个主交付物，不强制走大型团队的机会门、访谈、风险矩阵、Gate 和技术 Spike。

### 证据驱动

资料不是只作为附件保存，而是进入项目检索并通过 `[Sx]` 引用保留依据。原始 CSV、日志、政策或研究内容不会整份复制进正文，只在资料索引和相关结论处引用。F1 生成时，用户输入和当前项目资料是产品事实的唯一依据；历史知识、模板和其他产品案例只帮助组织结构，不能迁移成当前项目的市场、竞品、用户或商业化事实。引用已有交付物时，底层来源会展开和重新编号，避免旧引用失效。

### 可持续修改

交付物支持正文编辑、定位批注、修订任务和版本恢复，不需要每次从头重新生成。

### 项目隔离

不同项目的上传资料和已确认交付物不会混入彼此的项目检索。全局方法知识只作为只读补充。

### 安全可控

工作台不保存 Lanhu Cookie，不把工作台数据自动推送到 GitHub 或 Notion，也不会默认调用外部写入工具。

### 可扩展

能力通过 `capabilities/*.json` 和 Markdown 模板扩展；工具需要真实后端适配器，单纯在列表里添加名称不会自动获得能力。

| 定位批注和精确修订 | 已实现 |

## 9. 数据与安全注意事项

- `workbench/data/` 包含本地项目资料、运行记录和数据库，不应提交到 Git；
- 本地文件默认不加密，依赖电脑账户和文件权限保护；
- 不要把 Cookie、Token、账号密码或浏览器数据上传到项目资料；
- 生成任务会消耗本机 Codex 账号额度；
- 外部市场、价格和政策事实需要实时来源，不能把历史资料当成当前结论；
- 蓝湖、竞品后台和其他外部系统只能读取当前账号有权限看到的内容。

## 10. 后续扩展方向

优先级建议如下：

1. 在真实项目中完成评论采集、项目包跨电脑导入和导出视觉检查；
2. 增加检索过滤、来源时效提醒和知识候选沉淀；
3. 在同类任务重复出现后再增加新的能力包；
4. 完成 Lanhu MCP Bridge 的实际页面读取和连接测试。

不建议当前阶段优先做账号中心、多人权限、自动发布、投放管理或复杂后台。它们会显著增加维护成本，且不直接服务于小团队快速交付。
