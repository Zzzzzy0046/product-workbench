# 出海 C 端新品工作流使用手册

版本：V0.1  
更新日期：2026-09-09  
适用对象：产品经理、设计、研发、数据、QA，以及负责评审新品方向的决策者

## 1. 这套工作流解决什么问题

这套工作流用于把一个海外 C 端产品想法，逐步变成可以被设计、研发、数据和 QA 直接使用的交付物。

它解决的不是“如何把文档写长”，而是三个问题：

1. 这个方向是否值得继续投入；
2. 如果值得，第一版产品到底做什么、不做什么；
3. 每个角色拿到什么文件，凭什么进入下一阶段。

核心原则：

> 可以跳过已经完成的探索，但不能跳过阶段结论和交付物。

## 2. 适用范围与明确排除项

### 2.1 适用范围

- 海外 C 端 Android / Google Play 产品为主，iOS / App Store 为辅；
- 新品机会判断、竞品分析、产品定位、MVP、PRD、原型交接；
- 商业化设计、权限、隐私、平台政策和技术预研；
- 埋点、QA、设备验证、开发验收和后续迭代。

### 2.2 不包含的工作

以下内容不属于本工作流的交付范围：

- 付费投放和媒体采买；
- 投放归因和广告账户运营；
- ASO 文案、商店素材制作；
- Google Play / App Store 商店提交、发布和回滚执行。

平台政策仍然要分析，因为权限、隐私、订阅、广告和数据行为会直接影响产品设计。

## 3. 先理解两套编号

本工作流有两套编号，不能混用。

### 3.1 A 系列：工作流控制交付物

`A0–A7` 用来控制项目状态、Gate、责任和交接。

```text
A0 项目状态
  ↓
A1 机会判断
  ↓
A2 竞品证据
  ↓
A3 产品定义
  ↓
A4 PRD
  ↓
A5 原型交接
  ↓
A6 风险与决策
  ↓
A7 埋点 / QA / 验收
```

### 3.2 T 系列：产品经理实际工作交付物

`T1–T4` 是产品团队实际阅读和执行的文件。

| 编号 | 名称 | 作用 |
|---|---|---|
| T1 | 新品需求分析 | 从市场、用户、竞品一直分析到 Go / Hold |
| T2 | 产品框架与版本规划 | 把方向变成产品结构、MVP 和版本优先级 |
| T3 | 页面级 PRD 与原型交接 | 把功能和流程变成页面、状态、规则和设计交接 |
| T4 | 埋点、测试与验收 | 证明实现是否符合需求、体验和数据要求 |

两套编号的关系：

```text
T1 新品需求分析
  ├─ A1 机会判断
  ├─ A2 竞品证据
  └─ A3 产品定义

T2 产品框架与版本规划
  └─ A3 产品定义的详细执行版本

T3 页面级 PRD 与原型交接
  ├─ A4 PRD
  └─ A5 原型交接

T4 埋点、测试与验收
  ├─ A6 风险与决策
  └─ A7 验收包
```

不要把 A1 Opportunity Brief 当成完整的 T1 新品需求分析。A1 是 Gate 摘要，T1 是完整产品判断文档。

## 4. 四种使用模式

开始前，先判断项目属于哪一种模式。

### 4.1 全新想法

没有可靠的当前验证材料，从机会判断开始：

```text
A0 → T1 / A1 → A2 → A3 / T2 → A4 / T3 → A5 → A6 → A7 / T4
```

### 4.2 已经验证过的项目

已经有用户访谈、问卷、原型测试、Landing Page、真实数据或其他可靠证据：

```text
A0 更新状态 → 复核已有 A1 / A2 → 从最早未完成节点继续
```

不要重复做已经有证据支持的研究，但必须把证据、范围、时间和验证结论登记到 A0 和 Gate 记录中。

### 4.3 恢复已有项目

先读 A0 Manifest，再找到最早未完成或已失效的交付物。不要从聊天记录或最后一次修改位置直接猜下一步。

### 4.4 范围明确的小任务

例如“只写一个页面需求”“只补一个埋点表”“只检查权限风险”。只交付请求的文件，并在结果中列出上游缺口，不自动扩展成完整新品流程。

## 4.5 如何启动流程

### 4.5.1 在 Codex 或 Claude 中启动

新建一个任务，直接发送下面的启动指令，把方括号内容替换成实际信息：

```text
按“出海 C 端新品工作流”启动这个项目。

项目名称：[项目名]
产品想法：[一句话描述]
目标用户：[具体用户和使用场景]
目标市场：[国家 / 区域]
平台：[Android / iOS / 两者]
当前模式：[全新想法 / 已经验证 / 恢复已有项目 / 局部任务]
已有资料：[链接、文档、原型、数据；没有就写“暂无”]
本次目标：[希望得到的交付物]

执行要求：
1. 先读取当前项目的 A0 Manifest；没有就创建。
2. 使用 Product KB 检索相关方法、模板、历史决策和案例。
3. 判断当前阶段和最早未完成的交付物，不重复已经有可靠证据支持的工作。
4. 只执行当前阶段需要的工作，不提前扩展到后续阶段。
5. 输出本阶段交付物、Gate 结论、未解决风险和下一步最小行动。
6. 明确区分事实、推断、假设、决策、风险和待验证项。
```

### 4.5.2 已经验证过的项目

如果项目已经完成了用户访谈、问卷、原型测试、Landing Page 或真实数据验证，使用下面的补充说明：

```text
这个项目已经完成机会验证，请不要重复做基础机会探索。

已有验证结论：[写明验证了什么]
验证方法：[访谈 / 问卷 / 原型测试 / 数据 / 其他]
验证范围：[用户、区域、平台、样本量、时间]
实际结果：[结果和阈值对比]
仍未验证的内容：[方案、留存、付费、技术或政策风险]

请把已有证据登记到 A0，并从最早未完成的节点继续。
如果机会验证已经足够，直接进入 A3 Product Definition / T2；
如果核心方案也已经验证，评估是否可以进入 A4 PRD / T3。
```

### 4.5.3 恢复已有项目

```text
请恢复项目：[项目名或项目路径]。

先读取 A0 Manifest、最近一次 Gate 记录和未完成交付物，
判断当前项目状态，然后只继续最早未完成的节点。
不要从聊天记录的最后一句直接猜测下一步。
```

### 4.5.4 启动后的第一轮应该得到什么

一个正确的启动结果至少应包含：

- 当前模式和当前阶段；
- A0 是否创建或更新；
- 本轮要交付的文件；
- 需要复用的历史模板或知识；
- 当前 Gate 或待判断的 Gate；
- 证据缺口和风险；
- 下一步最小行动。

如果第一轮直接开始堆功能，却没有说明当前阶段和交付物，说明流程没有正确启动。

### 4.5.5 Product KB 未连接时

正常情况下 Codex / Claude 通过项目 MCP 配置读取 Product KB，不需要每次手动启动。

如果客户端提示 MCP 不可用，在 PowerShell 中进入 Product KB 目录执行：

```powershell
cd C:\PATH\TO\product-kb
.venv\Scripts\product-kb.exe doctor
.venv\Scripts\product-kb.exe search "新品需求分析方法和 Gate"
.venv\Scripts\product-kb-mcp.exe
```

如果只是执行当前项目工作，也可以在 MCP 暂时不可用时继续，但必须明确标注“本轮未执行 RAG 检索”，不能假装已经引用了知识库结果。

## 5. 完整交付物清单

### 5.1 A0 / 项目 Manifest

**目的：** 让任何接手者在一页内知道项目现在在哪里。

**必须包含：**

- 项目名称、负责人、日期、平台和目标区域；
- 当前工作流阶段；
- 已完成交付物及状态；
- Source of Truth 优先级；
- 已验证事实、当前假设和未决问题；
- 当前 Gate 结果；
- 阻塞项、负责人和触发条件；
- 下一步最小行动；
- Kill / Revisit 条件。

**完成标准：** 当前阶段、证据来源、阻塞点和下一动作都明确。

**文件建议：** `00-project-manifest.md`

### 5.2 A1 / Opportunity Brief

**目的：** 判断机会是否值得继续，而不是开始写功能。

**必须回答：**

- 目标用户是谁，处于什么具体场景；
- 用户正在付出什么成本；
- 为什么现在值得做；
- 第一次价值在什么时刻发生；
- 问题是否自然重复；
- 商业化是否和价值频率匹配；
- 最大的平台、技术、信任和安全风险；
- 如何验证，验证阈值是什么；
- 什么结果会导致收窄、暂停或终止。

**Gate：** G1 Opportunity Gate。

**允许结果：** `Go`、`Conditional Go`、`Hold`、`Stop`。

**文件建议：** `01-opportunity-brief.md`

### 5.3 T1 / 完整新品需求分析

这是 Heart Rate、PDF Reader、Printer 和 Doc Reader 历史模板整合后的完整新品分析文档。

**固定 0–12 章：**

| 章节 | 内容 |
|---|---|
| 0 | 文档信息与一页结论 |
| 1 | 行业与市场背景 |
| 2 | 用户分析 |
| 3 | 竞品与替代方案分析 |
| 4 | 产品定位与策略 |
| 5 | 产品范围与 MVP |
| 6 | 产品功能框架与详细需求 |
| 7 | 用户流程与关键体验 |
| 8 | 商业化策略 |
| 9 | 权限、数据、政策与产品边界 |
| 10 | 预研需求与关键依赖 |
| 11 | 指标、验证目标与迭代 |
| 12 | 最终决策 |

**写法要求：** 每章先给判断，再给证据和产品影响；明确区分事实、推断、假设、决策、风险和待验证事项。

**第 12 章必须有：**

- 现在必须做；
- 可以后置；
- 不要做；
- 三大风险；
- 下一步最小行动；
- Go / Conditional Go / Hold / Stop。

如果 G1 尚未通过，T1 后半部分可以写候选方案，但必须标记为“待验证”，不能伪装成已批准的产品需求。

### 5.4 A2 / Competitor Evidence Pack

**目的：** 把竞品观察变成可复核的产品判断。

**必须包含：**

- 竞品和替代方案清单；
- 平台、地区、版本和观察时间；
- 核心功能、用户路径、价格和限制；
- 用户评论或反馈证据；
- 竞品优势、弱点和空位；
- 对本产品定位、MVP 和风险的影响；
- 所有外部事实的链接和日期。

**完成标准：** 不是“列了几个竞品”，而是每条证据都能导出一个产品含义。

**文件建议：** `02-competitor-evidence-pack.md`

### 5.5 A3 / Product Definition

**目的：** 把机会变成边界清晰的产品。

**必须包含：**

- 一句话产品定位；
- 目标用户和核心使用场景；
- 核心价值闭环；
- 差异化理由；
- MVP 必须包含的能力；
- MVP 明确不包含的能力；
- 功能框架和版本优先级；
- 留存路径；
- 变现边界；
- 平台选择和平台差异；
- Kill / Defer 清单。

**Gate：** G2 Definition Gate。

**完成标准：** 研发能知道第一版做什么，设计能知道先画什么，产品能解释为什么不做其他功能。

**文件建议：** `03-product-definition.md`

### 5.6 T2 / 产品框架与版本规划

T2 是 A3 的可执行版本，适合正式进入设计和研发前使用。

**必须包含：**

- 产品信息架构；
- 核心模块；
- V0 / MVP / V1 / 后续版本边界；
- 功能优先级；
- 依赖关系；
- 技术预研安排；
- 每个版本的成功条件。

T2 不应该继续扩展想法，而应该收敛范围。

### 5.7 A4 / PRD

**目的：** 把产品定义变成可以执行和验收的需求。

**每个功能至少要写清楚：**

- 用户目标和触发条件；
- 页面或入口；
- 主流程；
- loading、empty、error、timeout、permission、interruption、restore 状态；
- 业务规则和边界条件；
- 免费 / 付费边界；
- 权限、隐私和数据行为；
- 依赖、异常处理和降级策略；
- 埋点要求；
- 验收标准。

**Gate：** G3 Solution Gate。

**文件建议：** `04-prd.md`

### 5.8 T3 / 页面级 PRD 与原型交接

**目的：** 让设计和研发拿到的是可检查的页面交接，而不是只有抽象功能名。

**必须包含：**

- 页面清单和页面 ID；
- 页面之间的跳转关系；
- 每个页面的目的；
- 正常、空、加载、失败、权限拒绝、网络异常、恢复等状态；
- 组件和交互说明；
- 中文需求描述；
- 必要的英文 UI copy；
- 视觉标注和尺寸规则；
- 页面与 PRD 需求 ID 的对应关系。

### 5.9 A5 / Prototype Handoff

**目的：** 完成产品、设计、研发之间的体验交接。

**交付内容：**

- 可访问的原型或页面文件；
- 页面地图；
- 关键流程演示路径；
- 页面状态说明；
- 组件 / Master / library 使用说明；
- 与 A4 PRD 的需求追踪表；
- 已知未覆盖状态。

**完成标准：** 设计稿不是孤立图片，每个关键页面和状态都能回溯到 PRD。

### 5.10 A6 / Risk & Decision Log

这是贯穿项目的交付物，不是最后才补的风险列表。

**每条记录包含：**

- 风险或决策描述；
- 类型：市场、用户、技术、政策、商业化、体验或数据；
- 事实和来源；
- 当前判断；
- 影响和严重程度；
- 负责人；
- 验证动作和截止条件；
- 触发后的回退阶段；
- Kill / Revisit 条件；
- 状态和最后更新时间。

### 5.11 A7 / Tracking, QA & Acceptance Pack

**目的：** 证明实现不仅“能打开”，而且符合需求、数据和平台行为要求。

**必须包含：**

- 埋点事件、参数、值域和触发时机；
- PRD / 原型 / 埋点的追踪关系；
- 主流程和异常流程测试用例；
- 目标设备和系统版本；
- 权限、订阅、广告和恢复行为验证；
- 崩溃、性能、兼容性检查；
- 已知缺陷和残余风险；
- 验收结论：`Accepted`、`Conditional` 或 `Rejected`。

**Gate：** G4 Development Acceptance Gate。

**文件建议：** `07-tracking-qa-acceptance.md`

### 5.12 T4 / 测量、测试与验收

T4 是 A7 的完整产品团队版本，包含：

- 关键指标定义；
- 事件和参数字典；
- 埋点验证；
- 测试计划；
- 设备与平台验证；
- 体验和异常恢复验证；
- 开发验收结论；
- 上线后需要观察的指标和风险。

## 6. Gate 怎么判断

### G1：Opportunity Gate

必须有：

- 明确的第一目标用户和具体场景；
- 可描述的痛点成本；
- 为什么现在值得做；
- 首次价值时刻；
- 自然重复路径；
- 与价值频率匹配的商业化可能；
- 主要政策和技术风险；
- 可证伪的验证阈值。

没有这些内容，不能因为“功能看起来有意思”就进入 PRD。

### G2：Definition Gate

必须有：

- 清晰定位；
- 可感知差异化；
- 有边界的 MVP；
- 留存逻辑；
- 变现逻辑；
- 平台决定；
- 明确的 No-build 清单。

### G3：Solution Gate

必须有：

- 端到端主流程；
- 主要异常和恢复状态；
- 业务规则；
- 免费 / 付费边界；
- 权限和隐私；
- 技术预研结果或负责人；
- 验收标准；
- A3–A6 之间的追踪关系。

### G4：Development Acceptance Gate

必须有：

- 目标设备上的核心价值路径；
- PRD、原型、实现一致；
- 埋点事件、参数和值正确；
- 订阅、广告、权限行为正确；
- 异常恢复可用；
- 崩溃、性能和兼容性检查；
- 残余问题清单。

### G5：Iteration Gate

只有已经有真实产品数据时才使用。

至少要看：

- 激活；
- 留存；
- 核心价值完成率；
- 变现；
- 质量和崩溃；
- 政策或信任护栏。

结果为 `Continue`、`Iterate`、`Hold` 或 `Retire`。

每个 Gate 的记录都必须包含：结果、依据、未通过项、负责人、回到哪个阶段、下一步最小行动和 Kill / Revisit 条件。

## 7. 已验证项目的直达规则

“已经验证过”不能只写一句结论，至少要有以下信息：

- 验证了市场、痛点、方案、留存还是付费；
- 验证方法；
- 用户、区域、平台和样本范围；
- 验证时间；
- 成功阈值和实际结果；
- 尚未验证的风险。

然后按验证深度选择起点：

| 已有证据 | 起点 |
|---|---|
| 只证明用户有问题 | A3 / 产品定义 |
| 证明用户愿意尝试方案 | A3 + T2 / MVP 设计 |
| 证明核心流程和首次价值 | A4 / PRD 或 T3 / 原型 |
| 已有真实产品数据 | G5 / 产品迭代 |

必要的跳过方式：

```text
不要跳过：A0 状态记录、Gate 结果、风险和下一步
可以复用：已有 T1 章节、A2 竞品证据和验证材料
可以跳过：已经完成且仍然有效的重复研究
```

## 8. 一次完整使用流程

### 第一步：建立 A0

先写清楚项目现状，不要直接开始罗列功能。

### 第二步：读取 Product KB

检索方法、模板、历史决策和相似案例。检索结果只作为参考，优先级始终是：

```text
当前用户确认
  > 当前源文件 / 原型 / 真实行为
  > 当前项目确认文档
  > 有日期的历史知识
  > 通用模板
```

每次引用知识时，标记它是事实、历史方法、推断还是当前决策。不要把历史案例当作当前产品事实。

### 第三步：确定起点

判断项目是全新、已验证、恢复还是范围明确的小任务，然后选择最早未完成的节点。

### 第四步：产出当前节点交付物

只解决当前节点的问题，不因为发现一个功能点就提前写完整 PRD。

### 第五步：做 Gate 判断

Gate 结果必须有证据、缺口、负责人和下一步，不允许只写“通过”。

### 第六步：更新 A0 和 A6

同步项目状态、决策、风险和下一动作，保证接手者不需要重新阅读全部聊天记录。

### 第七步：交接并停止在正确位置

没有真实产品数据时，不提前进入 G5；没有完成方案闭环时，不提前做高保真原型；没有通过 G1 时，不进入研发型 PRD。

## 10. 最小交付标准

### 如果项目停在 G1

至少应留下：

- A0；
- A1；
- T1 已完成的章节；
- 证据来源；
- G1 结果；
- Kill / Revisit 条件；
- 下一步最小验证动作。

### 如果项目进入产品定义

至少应留下：

- 完整 T1；
- A2；
- A3；
- T2；
- G2 结果；
- MVP 和 No-build 清单。

### 如果项目进入研发

至少应留下：

- A4 / T3；
- A5 原型交接；
- A6 风险与决策；
- A7 / T4；
- G3 和 G4 结果。

## 11. 常见错误

### 错误一：把 A1 当成完整新品分析

A1 只负责机会 Gate。完整的 0–12 新品需求分析是 T1。

### 错误二：验证过痛点就直接写 PRD

痛点成立不等于解决方案成立。至少还要明确 MVP、核心流程、政策边界和技术可行性。

### 错误三：竞品列表很多，但没有产品结论

每个竞品事实都必须回答“这对我们的定位、MVP 或风险意味着什么”。

### 错误四：把候选功能写成已批准需求

G1 Hold 或 Conditional Go 时，候选功能必须标记为待验证。

### 错误五：只写正常流程

没有 loading、empty、error、timeout、permission、interruption 和 restore，PRD 就还没有闭环。

### 错误六：把模板、历史案例和当前事实混在一起

模板告诉我们怎么写，历史案例告诉我们曾经怎么判断，当前证据才决定现在做不做。

## 12. 交付前自检清单

### 方向

- [ ] 目标用户具体；
- [ ] 使用场景具体；
- [ ] 问题成本可描述；
- [ ] 首次价值明确；
- [ ] 重复使用理由成立；
- [ ] 变现和价值频率匹配。

### 范围

- [ ] MVP 有边界；
- [ ] 明确了不做什么；
- [ ] 没有用功能堆叠掩盖方向问题；
- [ ] 版本优先级明确。

### 体验与实现

- [ ] 主流程闭环；
- [ ] 异常状态闭环；
- [ ] 权限、隐私和数据行为明确；
- [ ] 技术预研有结果或负责人；
- [ ] 页面和需求可以相互追踪；
- [ ] 验收标准可执行。

### 决策

- [ ] Gate 结果明确；
- [ ] 事实、推断、假设和决策分开；
- [ ] 风险有负责人和触发条件；
- [ ] 下一步是一个最小、具体的动作；
- [ ] 不值得继续时有 Kill / Retire 条件。

## 13. 一句话记忆法

```text
A0 管状态
A1 判机会
A2 找证据
A3 定产品
A4 写规则
A5 交体验
A6 管风险
A7 做验证

T1 讲清楚为什么做
T2 讲清楚先做什么
T3 讲清楚怎么做出来
T4 讲清楚是否做对了
```

最终目标不是产出最多的文档，而是让每一个阶段都留下一个可以被下一个阶段直接使用的交付物。
