# 数据采集能力与数据流：同事交接说明

版本：v1.0　｜　日期：2026-10-22　｜　本次范围：数据采集、整理、归档与导出

## 1. 本次要做成什么

**给定 App、市场及采集范围，工具或 Agent 完成资料采集，交出带来源、采集条件和覆盖说明的标准资料包，供其他同事或后续工具直接使用。**

按白板思路，采集对象分为四类：评论、商店资料与宣传截图、App 实机页面与流程截图、留存/画像等外部数据。原图部分内容不清晰，本说明只围绕这些可辨识来源展开。

本次交付终点是“资料包可用”：能找到原始文件，知道采了什么、没有采到什么，并能继续补采。评论分析、竞品判断、产品决策、F1、PRD、原型、埋点及产品验收均留给后续使用方。

若沿用 SSOT 一词，本阶段仅指资料的统一出处与索引，先维护原始资料、标准记录和来源关系；产品规则、决策基线及跨需求文档同步不进入本轮。

### 1.1 本轮能力拆分

| 编号 | 能力 | 用户提供什么 | 最终得到什么 |
|---|---|---|---|
| C01 | 评论采集 | App、市场/语言、取样与筛选条件 | 原始评论、标准评论表、可选译文、样本与缺口说明 |
| C02 | 商店资料与宣传图采集 | App 链接/ID、商店市场和语言 | 元数据、长短描述、宣传图原文件、来源记录 |
| C03 | 指定范围的 App 实机截图 | Android App、设备及需要走查的模块/路径 | 原始截图、页面状态、真实操作记录、模块流程 PNG、覆盖地图 |
| C04 | 外部数据导入与来源记录 | 数据文件/报表或明确的数据来源、指标和周期 | 原始数据、标准表、指标口径、覆盖与缺口 |
| C05 | 共用整理、归档和导出 | 前四类采集结果 | 去重后的标准资料、原件索引、任务清单、可下载资料包 |

评论与商店资料可以共用采集后端；截图 Skill 与自动 runner 是 C03 的执行方式；C05 是四类来源共用的处理能力。不要求为每个能力单独建立网页或服务。

## 2. 数据怎么流动

~~~mermaid
flowchart TD
    T[采集任务：App、市场、范围、输出要求] --> C1[C01 评论]
    T --> C2[C02 商店资料和宣传图]
    T --> C3[C03 指定范围实机截图]
    T --> C4[C04 外部数据导入]
    C1 --> R[先保存原始资料和采集条件]
    C2 --> R
    C3 --> R
    C4 --> R
    R --> N[C05 解析、可选翻译、去重、字段整理]
    N --> I[标准记录、来源索引、实际覆盖与缺口]
    I --> P[导出资料包：原件、表格、图片、地图和采集说明]
    P --> U[交给人或其他工具使用]
    I -. 按缺口补采 .-> T
~~~

四条来源链可以独立运行。没有留存数据，也可以完整交付评论与截图；某个市场或一条分支失败，应保留其他已成功结果。补采创建新的采集记录并关联旧任务，原始记录不静默覆盖。

## 3. 输入：用户需要给到什么程度

### 3.1 共用采集任务

| 字段 | 说明 |
|---|---|
| 对象 | App 名称及链接/包名/App ID、平台；批量任务逐个列明 |
| 来源类别 | 评论、商店资料、实机截图、外部数据；按需选择 |
| 范围 | 市场/语言、日期与条数、模块/路径、指标/周期等对应条件 |
| 输出 | 是否需要译文、模块拼图，以及要交付的文件类型 |
| 归属 | 项目或资料集合、任务 ID；没有产品版本也能发起研究采集 |

工具从来源读取版本、开发者、设备等可获取字段，不要求用户重复填写。只有对象有歧义、必要来源不可用或出现范围外操作时才补充确认。

### 3.2 两种示例指令

**商店与评论：**采集指定 App 在 US 商店的介绍、宣传截图及最近一段时间的低分评论，保留原文，另给中文译文。需要记录请求条件、抓取样本量、筛选后数量和缺失字段。

**实机截图：**走查指定 Android App 的“首页 → 导入 → 返回，以及设置页”，按模块保存页面和关键状态，生成流程 PNG。未走到的分支单列；系统页、登录或购买等范围外操作暂停交接。

实机入口应支持“给 App 和范围后由 Agent 执行常规走查”。用户不需要逐个指定按钮；执行方根据当前画面决定下一步，并遵守范围、预算和暂停条件。

## 4. 各项能力说明

### C01 评论采集

| 项目 | 交接约定 |
|---|---|
| 输入 | App 链接/ID、平台、市场/语言、排序/日期/评分/关键词等条件、取样数量、是否翻译；也可导入已有文件 |
| 处理 | 定位 App → 保存请求条件 → 抓取原始样本 → 字段校验与精确去重 → 按条件筛选 → 按需翻译 → 汇总采样与失败情况 |
| 输出 | 评论原始结果、标准 CSV/JSON、可选译文、采集来源与条件、实际条数、去重/筛选统计及缺口 |
| 最少字段 | 来源评论 ID、App/平台、原文、评分、发表时间、来源返回的语言/版本等字段；原文与译文分列，未知项留缺 |
| 衔接 | 送 C05 统一归档和导出；使用方可以据此做评论分析，采集器本身不生成需求优先级 |
| 完成标准 | 任意记录能回查原始结果；能说明采样和筛选范围；翻译失败不丢原文；空结果与抓取失败可区分 |

筛选通常作用于已抓取样本，不能保证筛选后仍达到指定条数。记录“请求数量、实际抓取数量、筛选后数量”，不可把样本写成全量评论。商店市场和评论语言不等于评论作者国籍；用户在评论中报告的问题不等于已经复现。

### C02 商店资料与宣传图采集

| 项目 | 交接约定 |
|---|---|
| 输入 | 指定 App 链接/ID、平台、商店市场和语言，需要采集的文案/元数据/图片字段 |
| 处理 | 核对对象 → 读取公开页面/接口 → 保存原始响应或快照 → 整理文案与元数据 → 下载宣传图并保留顺序 → 标记缺失 |
| 输出 | 商店资料 JSON/Markdown、宣传图原文件、来源链接、采集时间、市场/语言、字段缺口；译文为可选派生资料 |
| 最少字段 | App ID、名称、开发者、平台、市场/语言、来源及时间；长短描述、评分、版本等按来源实际返回保存 |
| 衔接 | 与 C01 按 App/市场/批次关联；送 C05。与 C03 的实机图分别标识和存放 |
| 完成标准 | 没有混淆同名 App；文案可回查；图片可打开、顺序可追溯；未返回字段不拼凑补写 |

宣传图只说明商店展示了什么。短描述或副标题缺失时留空，不拿长描述或其他字段代替。某个市场无法访问时记为该市场缺口，不用另一市场内容静默代替。

### C03 指定范围的 App 实机截图

| 项目 | 交接约定 |
|---|---|
| 输入 | 已安装 Android App 的包名、选定设备、需要走查的模块/路径、起止与停止条件；必要时提供虚构测试数据 |
| 处理 | 确认设备/App/版本 → 读取当前 UI → 确认页面并截图 → 选择范围内操作 → 读取操作结果并截图 → 标记模块/页面/状态与已执行路径 → 按模块导出 |
| 输出 | 原始 PNG、可用时的 UI XML/JSON、操作记录、页面/状态地图、已验证跳转、模块流程 PNG、未覆盖分支与暂停原因 |
| 最少字段 | 任务、设备、App/版本、观察时间、截图位置、模块/页面/状态、动作及对应结果；人工操作与工具执行分开记录 |
| 衔接 | 送 C05；流程 PNG 引用原始截图，不能只有拼图而丢单图；后续工具按地图读取资料 |
| 完成标准 | 每个流程节点有原图，每条确定跳转有动作及结果依据；范围覆盖可对照；没执行的路径不画成已走通 |

**执行方式：**

- 目标入口是“给范围的 Skill/Agent 走查”：Agent 按协议观察、操作、记录，自动整理模块与状态。Skill 交给其他 Agent 时，应适配实际可用工具与脚本，不绑定某一段对话。
- 现有工作台自动 runner 可作为实现参考；它依赖当前 Codex/模型/ADB/设备环境。已有合成回归和受限冒烟记录，真实目标 App 自动完整走查仍需验证。
- 独立采集器已有人工选择控件的半自动截图入口，可作为单独模式和人工接管方式，不等同于上述自动走查。

**中断与恢复：**登录、购买、系统页、设备断开、范围外页面、结果不确定或预算用尽时暂停，保留已采资料和缺口。恢复时先重新确认设备、版本和当前画面；已发出但结果未知的动作不能直接重复。人工在手机上操作后，可以记录新画面，但不能推断中间动作或补画工具已验证的跳转。

首版聚焦 Android 已安装 App。iOS 商店资料采集与 iOS 实机操作是不同能力；现有 Android 方案不能直接宣称支持 iOS 实机。截图和控件记录也不证明支付、埋点或收入结果。

### C04 外部数据导入与来源记录

| 项目 | 交接约定 |
|---|---|
| 输入 | 用户提供的文件/报表、已有可访问来源；App、指标、地区、平台、周期与数据定义 |
| 处理 | 保存原件 → 记录来源和时间 → 解析字段 → 核对指标口径/单位/覆盖 → 整理为可读表 → 标记缺失和不可比较项 |
| 输出 | 原始文件/快照、标准数据表、字段与指标说明、实际值/估计值标识、来源及缺口 |
| 最少字段 | 对象、指标、数值/区间、单位/币种、统计周期、地区/平台、来源时间、实际或估算、样本/覆盖及计算口径 |
| 衔接 | 送 C05 归档。数据可用性说明交给后续使用方，采集层不负责给收入、留存或市场结论 |
| 完成标准 | 数字可回查原始来源；时间和单位明确；缺失不写成 0；不同口径不静默合并 |

留存至少说明 cohort、回访事件、时间窗口与分母；画像说明样本、分类与覆盖；收入区分广告/IAP/合计、毛净口径和币种；下载区分安装量、期间新增等定义。采集时间与数据所属周期分别记录。

**首版建议先支持导入与口径记录。**自动接入具体平台需要明确数据来源、访问方式和实际可取得字段后再列专项需求。当前没有自动接入留存、画像、广告收入或投放数据的完整能力；不能用评论、商店安装量或截图补成这些指标。

### C05 共用整理、归档和导出

| 项目 | 交接约定 |
|---|---|
| 输入 | C01—C04 的原始结果、采集条件、执行记录及失败信息 |
| 处理 | 原件留存 → 按来源解析 → 字段标准化 → 精确去重 → 可选翻译/图片拼接 → 建来源索引 → 核对文件与覆盖 → 导出 |
| 输出 | 原件、标准表、图片及地图、来源索引、任务 manifest、数量/覆盖与失败报告、单文件或 ZIP |
| 去重规则 | 同文件可按内容摘要识别重复，评论按 ID/内容识别重复；相似文本/图片不自动删除，不合并不同版本/市场/页面状态 |
| 衔接 | 向人或其他工具交资料包；补采时沿用对象及来源关系，保留旧批次与新批次 |
| 完成标准 | 所有导出引用都有对应文件；原文/译文和商店图/实机图区分；重复可解释；成功、失败、缺失和未覆盖明确 |

本层可以做翻译、格式化、模块标注、页面转写和数据质量检查；不判断竞品优劣、不推断问题原因、不生成产品方案。通用语义去噪不是首版前提，应先把精确去重和可追溯整理做好。

## 5. 资料包与交接约定

以下是建议输出结构，不表示本轮已经改动工具的文件布局；落地可映射到已有目录，保持内容含义一致即可。

~~~text
collection-<任务ID>/
  manifest.json                 请求、实际执行、数量、覆盖、失败与文件索引
  README.md                     本批次说明、阅读顺序与缺口
  raw/                          原始响应、导入数据及来源快照
  store/                        商店标准资料与宣传图
  reviews/                      原始/标准评论及可选译文
  app-capture/                  实机单图、控件信息、操作记录、地图与流程PNG
  external-data/                外部指标标准表及口径说明
  source-index.csv              来源编号与记录/文件的对应关系
~~~

本轮没选择的类别不必生成空目录。原始实机图可以直接保存在 app-capture 中，不要求为目录形式再复制一份。

### 5.1 共用回执与 manifest

| 内容 | 必须表达什么 |
|---|---|
| 身份 | 任务 ID、项目/资料集合、App ID/包名、平台、执行的能力 |
| 请求条件 | 市场/语言、日期、数量、筛选、模块/路径、数据周期等 |
| 实际条件 | 真正使用的来源、设备/App 版本、采集起止时间 |
| 执行结果 | 成功、部分成功、暂停或失败；逐 App/市场/模块记录，不只写整批“完成” |
| 实际覆盖 | 请求与取得数量、筛选/去重数量、已走查页面/分支、未覆盖内容 |
| 文件与来源 | 原件/标准记录/派生文件位置、稳定来源编号、记录 ID、原件与派生关系 |
| 问题与续采 | 失败原因、缺失字段、暂停点、可补采项及恢复所需条件 |

字段未知时注明未知，不能凭文件名补猜。来源/记录编号在同一资料集合内稳定；重新导出不换号，新增批次保留与旧记录的关联。

### 5.2 使用方怎样接收

使用方先读 README 和 manifest 了解批次范围，再从标准表或地图找到目标记录，通过来源索引回到原始文件。这样人、Claude/Codex 等 Agent 或其他分析工具可以消费同一资料包，无须依赖原采集对话。

任务完成不表示目标 App 全部路径已覆盖；资料导出成功也不表示数据支持任何经营或产品结论。回执只报告本次采集事实与缺口。

## 6. 当前基础与推荐建设顺序

### 6.1 可以交给同事复用的资产

以下路径相对于工作台项目根目录。

| 能力 | 现有资产 | 当前边界 |
|---|---|---|
| C01/C02 | packages/competitor-collector/；工作台竞品采集入口 | 已有独立网页/CLI/Python 采集包；两入口共用核心，但工作台仍可走 legacy 桌面后端，移交需对齐字段、默认值及依赖 |
| C03 人工 | packages/competitor-collector/competitor_collector/android_capture.py | 已有人选择控件的半自动截图、标注、地图与拼图；不是自主走查 |
| C03 Skill | android-app-screenshot Skill；packages/android-capture/skill/ 协议/脚本 | 可复用受控走查流程；脚本副本不是独立软件或自动 runner，跨 Agent 需要适配工具 |
| C03 自动 | workbench/services/android_capture_service.py；workbench/adapters/android_capture_runner.py；workbench/capture_mcp.py | 已实现工作台自动编排基础；真实目标 App 覆盖和稳定性仍需实测 |
| C04 | workbench/services/competitor_revenue_service.py；资料导入 | 现有主要是人工记录与上传；没有自动经营数据连接器 |
| C05 | workbench/services/material_service.py；采集器结果、manifest 与导出 | 已有解析、精确去重、翻译分列和归档基础；跨入口的统一资料包仍需收拢 |

本轮以“采集能力与资料包”为交接单位，不要求把原工作台后面的需求生成模块一起迁入。具体实现可复用现有代码，也可由同事按同一输入输出约定独立实现。

### 6.2 推荐顺序

1. **先打通评论＋商店资料＋标准导出。**复用现有采集核心，统一 App/市场/批次/来源与文件索引，验证资料包可供外部读取。
2. **把截图 Skill 接成给范围的采集任务。**保留已有人工截图入口，补齐自动执行、暂停恢复、真实 App 走查验证，以及与资料包的统一衔接。
3. **支持外部数据导入与口径记录。**先接用户实际已有文件；明确首个必需平台后再做自动连接器。

首轮是否完成，可用以下行为判断：

| 场景 | 预期 |
|---|---|
| 给 App 与市场采商店/评论 | 有原件、标准表、条件及实际数量；不存在的字段保留缺失 |
| 给模块范围做实机采集 | 有单图、状态、真实路径与拼图；范围外或失败分支有说明 |
| 同批次部分失败 | 成功资料保留，可按失败部分重试；不覆盖其他来源结果 |
| 重复导入或补采 | 重复可识别，新增有批次记录，原件与上下文不丢 |
| 没有外部经营数据 | 缺口明确，其他采集继续交付，不补造指标 |
| 把资料包交给另一位同事/Agent | 对方仅凭资料包就能定位对象、理解范围、找到原件与缺口 |

**本阶段的完成定义：给范围，拿资料；原件可查，结果可用，缺口可见，任务可续。**
