# 产品工作台：能力总览与数据流交接说明

版本：v1.0　｜　日期：2026-10-22　｜　面向：产品、设计及负责落地的研发同事

> 当前交接范围已收敛为数据采集，请使用同目录的《数据采集能力与数据流-同事交接说明-v1.0.md》。本文保留作完整工作台能力参考。

## 1. 这份说明要交接什么

工作台的目标是：**把评论、商店展示、App 实机体验及外部数据整理成可追溯的产品依据，再围绕同一套已确认规则生成分析、流程、原型说明、PRD、埋点和验收材料。**

本说明交接能力定义、数据如何流动、模块之间如何配合，以及什么结果算完成。实现同事可据此拆模块、确定接口和安排建设；本文不预设语言、数据库、模型厂商或部署架构。

白板图可辨识的主要节点是“评论、商店截图、App 截图、留存/画像等数据、Skill、SSOT”。图右侧及底部部分内容不清晰，本文将其展开为“来源采集 → 保留原始证据 → 标准化整理 → SSOT → 产品产出 → 一致性检查”的建议流程，不能把展开内容当作白板原文。

**需要先对齐的三个判断：**

1. 能力可以独立调用，数据约定需要共用。一次任务可以只做评论整理，也可以从已有产品基线直接开始版本迭代，无须每次跑完整流程。
2. 原始证据、分析判断、已确认方案是三种内容。采集成功不代表分析成立，方案被确认也不代表原型或 App 已经改好。
3. 当前已有工具、脚本、模板和部分编排基础，但八组能力尚未全部形成独立工具。第 11 节单独说明现有资产与建设边界；第 2—10 节描述应交付的行为。

### 1.1 八组能力

| 编号 | 能力 | 负责回答的问题 | 主要交付 |
|---|---|---|---|
| C01 | 评论资料采集 | 用户在评论中具体说了什么？本次取样覆盖哪里？ | 原始评论、可选译文、采样与缺口说明 |
| C02 | 商店资料采集 | 竞品在商店如何描述、展示和销售自己？ | 商店元数据、文案、宣传截图、来源记录 |
| C03 | App 实机走查 | 在指定版本、设备和范围内，实际看到什么、操作后发生什么？ | 实机截图、页面状态、已走查路径、模块流程 PNG、未覆盖项 |
| C04 | 外部数据整理 | 留存、画像、下载、收入等数据来自哪里，按什么口径计算？ | 带来源和口径的数据资料包、可比较范围及缺口 |
| C05 | 标准化与去噪 | 如何把不同来源整理成能检索、能引用、不会丢证据的材料？ | 标准化记录、证据索引、去重映射、质量与冲突标记 |
| C06 | SSOT 管理 | 当前采用什么事实、判断和规则？依据、适用版本及确认情况是什么？ | 当前基线、证据与判断索引、公共规则、待决定项、变更记录 |
| C07 | 分析与产品方案产出 | 这些依据对我方产品意味着什么，本轮具体做什么？ | 竞品分析、F1、版本简报、流程、原型交接、F2、埋点、验收及复盘 |
| C08 | 一致性与交付检查 | 各产物是否使用同一口径，哪里冲突、缺失或尚未同步？ | 可定位的问题清单、修订内容、影响范围、同步与核对结果 |

## 2. 总数据流

~~~mermaid
flowchart TD
    T[本轮任务：对象、范围、问题、目标产出] --> C1[C01 评论]
    T --> C2[C02 商店资料]
    T --> C3[C03 实机走查]
    T --> C4[C04 外部数据]
    C1 --> R[原始资料区：原文、图片、数据文件和采集记录]
    C2 --> R
    C3 --> R
    C4 --> R
    R --> C5[C05 标准化、去重、索引、覆盖与质量检查]
    C5 --> E[C06 SSOT：证据与观察、分析判断、当前确认基线]
    K[历史知识：方法、模板、过往案例] -. 提供结构与参考 .-> C7
    E --> C7[C07 按需分析和方案生成]
    C7 --> D[草稿：分析、范围、规则、流程、原型说明、PRD、埋点、验收]
    D --> C8[C08 一致性检查与修订]
    E --> C8
    C8 --> Q[产品负责人确认本轮采用内容]
    Q --> E
    Q --> H[交付包：当前正文、来源快照、已知缺口、待同步项]
    X[外部原型修改或构建实测结果] --> R
    N[来源新增、纠正、失效或评审意见] --> R
    E -. 基线变更：列影响范围 .-> C8
~~~

图中的回路按本轮范围运行。评论、商店、实机和外部数据可以并行，缺少其中一类不必阻断所有工作；但依赖该类证据的结论必须保留缺口。历史方法与模板只帮助组织内容，不能补造当前产品事实。

### 2.1 各阶段的交接约定

| 从哪里到哪里 | 交过去什么 | 接收方可以做什么 | 不能省略什么 |
|---|---|---|---|
| 任务入口 → C01—C04 | 项目、研究对象、平台、范围、市场/语言、版本要求和本轮问题 | 按约定取样或走查 | 明确对象及边界，不把“看一下 App”扩成无范围探索 |
| C01—C04 → 原始资料区 | 原文件及采集记录，成功项与失败项分开 | 保存和重试 | 来源、时间、请求范围、实际覆盖、失败原因 |
| 原始资料区 → C05 | 稳定来源编号和原始材料 | 解析、翻译、去重、结构化 | 原文、原图、原始数据可回查 |
| C05 → C06 | 标准记录、来源映射、观察、缺口与冲突 | 入索引并按类型组织 | 不把推断装成观察，不把缺失数值写成 0 |
| C06 → C07 | 本轮选用的资料快照、当前基线、规则和待决定项 | 生成限定范围的分析或方案 | 记录实际使用了哪些来源和基线版本 |
| C07 → C08 | 草稿及其来源、页面/状态/规则等引用 | 核对遗漏、冲突及改动影响 | 检查必须能定位到正文或具体外部页面 |
| C08 → 确认与交付 | 修订稿、未解决项、影响和待同步位置 | 确认本轮采用内容，交给下一角色 | “文档确认”“外部已同步”“实测通过”分别记录 |
| 新证据/新决定 → 已有产物 | 新旧差异和受影响关系 | 只更新受影响内容并复查 | 保留历史快照，不能静默覆盖旧结论 |

## 3. 所有能力共用的输入与输出约定

本节是产品层面的数据约定。字段可以落在表、文件或接口中，不要求每类内容都拆成一套系统。

### 3.1 本轮任务单

| 项目 | 必须说明的内容 | 缺失时如何处理 |
|---|---|---|
| 归属 | 我方项目、本轮产品版本或研究阶段 | 未确定版本可按项目研究资料保存，不能擅自归入某个线上版本 |
| 对象 | App 名称及包名/App ID、平台；区分我方产品与竞品 | 对象有歧义时先定位；不得混合两个同名 App |
| 目标 | 要回答的问题、准备生成什么产物 | 使用本轮已说明目标；没有目标时先交资料包，不扩写完整方案 |
| 范围 | 模块、流程起止点、评论条件或数据指标；包含项与排除项 | 保留实际范围，不把局部材料称为全量 |
| 环境 | 商店市场/语言，或设备、App 版本、账号状态等必要条件 | 未知字段注明未知；商店国家不等于设备所在地，也不等于评论用户国籍 |
| 来源 | 链接、已有文件、已安装 App、已提供数据或已确认文档 | 无可访问来源时标记缺失，不生成替代事实 |
| 输出偏好 | 资料/图片/分析/需求等；是否需要翻译、拼图 | 默认只输出本轮需要内容；翻译、分析和采集分别可选 |

### 3.2 最小记录类型

| 类型 | 核心内容 | 示例编号 | 用途 |
|---|---|---|---|
| 来源与证据 | 对象、原始内容位置、来源类型、时间、环境、采样范围、采集状态 | SRC-001 / EVD-001 | 回到原文、原图、原数据，支持复核 |
| 观察 | 在哪些证据和条件下，直接看到或执行了什么 | OBS-001 | 陈述可核对现象，保留适用范围 |
| 分析判断 | 基于哪些观察形成什么解释、推断或建议，哪些仍未验证 | FIND-001 | 分析、方案推演，不直接成为产品规则 |
| 决定与规则 | 谁在何时确认什么，适用产品/版本、触发条件、例外和失效条件 | DEC-001 / RULE-001 | 规定我方产品当前应如何表现 |
| 基线 | 本轮采用的证据、规则和已确认产物版本的集合 | BL-001 | 固定生成与评审依据，支持前后对照 |
| 交付物 | 正文、类型、修订版本、采用基线、来源引用、确认状态和待同步项 | DOC-001 | 交给下一角色使用 |
| 变更 | 新旧口径、理由、确认依据、影响位置和同步情况 | REV-001 | 关联同一次修改，避免多份清单各写一套 |

编号是引用约定示例，已有编号应沿用；同一对象不因重新导出就换号。文内 S1/S2 等简短引用应能映射回稳定来源编号。同一原文被多处使用，保留多个使用关系即可。

D04“产品基线”是产品现状与约定的整理成果；BL“本轮采用基线”是一次任务选用哪些证据、规则及产物版本的快照。D04 可以被纳入 BL，两者不等同。新项目尚无确认方案时，BL 可先只包含本轮任务与已选证据，明确当前规则为空或待决定，不要求先有完整 PRD 才能分析。

每条证据至少保留：所属项目、研究对象、来源类型、原始内容位置、获取时间、内容所属时间或版本、采集范围、实际覆盖与缺口。涉及来源链接、页码、CSV 行、截图文件、页面状态、设备或操作记录时，补齐相应定位信息。无法确定的字段显式留缺，不根据文件名或上下文猜测。

### 3.3 内容身份与状态分开

| 维度 | 可用状态或类型 | 含义 |
|---|---|---|
| 内容类型 | 原始证据 / 观察 / 推断 / 建议 / 已确认规则 | 区分这句话依据是什么、能用来证明什么 |
| 采集任务 | 成功 / 部分成功 / 暂停 / 失败 | 描述执行情况，保留具体原因和已完成项 |
| 产品稿件 | 草稿 / 待评审 / 需修改 / 已确认 / 已被替代 | 描述是否可作为当前约定；被替代稿仍可回看 |
| 外部同步 | 不涉及 / 待同步 / 已写回待核对 / 已核对 | 描述原型或其他外部对象是否真正修改并读取核验 |
| 实测 | NOT_RUN / 已测通过 / 已测失败 / 受阻 | 仅用于有明确构建、环境、操作和证据的测试记录 |

工作台中的“已确认”只表示该稿或该规则被接受作为后续依据。公司评审通过、研发完成、外部原型已改、App 实测通过、商业结果成立各有独立证据，不合并为一个“完成”。

### 3.4 每次能力调用统一交回什么

无论由脚本、人工、Skill 还是 Agent 完成，接收方都应拿到同样含义的回执。Skill 负责规定处理方法，项目事实与当前基线由共用资料管理，不应只留在某次模型对话里。

| 回执内容 | 必须能回答的问题 |
|---|---|
| 任务与能力 | 哪个项目、哪个对象、本轮范围、调用哪项能力？ |
| 采用输入 | 实际读取了哪些文件、记录或基线版本？其中哪些要求尚未满足？ |
| 产出清单 | 生成哪些文件/记录、稳定编号和类型？到哪里查看？ |
| 来源关系 | 每项观察、结论或产物对应哪些底层证据和规则？ |
| 执行与覆盖 | 成功、部分成功、暂停或失败？实际处理多少、覆盖哪里、停在哪里？ |
| 缺口与下一步 | 什么尚未得到、不能判断或需要决定？能否按缺口重试，下一项能力应接收什么？ |

这种回执用于衔接，不新增业务审批步骤。采集成功、稿件确认、外部同步和实测状态继续按第 3.3 节分别记录。

## 4. C01—C04：来源能力

### C01 评论资料采集

**目标：**获得可追溯、可筛选的用户原话，为后续问题归类与竞品判断提供材料。评论采集不直接承担需求优先级判断。

| 项目 | 约定 |
|---|---|
| 输入 | 明确 App 与平台、商店市场/语言、日期/评分/关键词/数量或取样条件、排序方式、是否翻译；也可导入已有评论文件 |
| 输出 | 原始评论文件、标准化评论表、可选中文译文、来源与采样说明、失败及缺口清单 |
| 处理思路 | ①记录请求条件；②采集或导入原始结果；③保留评论 ID、原文、评分、日期、语言及来源中实际存在的版本等字段；④做精确去重与字段校验；⑤按需翻译并单独存列；⑥输出请求范围与实际覆盖差异 |
| 上下游 | 接任务单；送 C05；经 C06 后，供 C07 评论分析、竞品分析和 F1 使用 |
| 资料不足时 | 无法访问、缺少版本/地区等字段、评论数量不足均明确记录；保存可用部分，允许针对缺口重试 |
| 完成标准 | 能从表内任意一条回到原始评论；能看出筛选/排序/取样条件；原文与译文不混；实际数量和去重数量可解释 |

**边界：**评论是样本中的用户表达，不能直接代表全部用户的画像比例、问题发生率、留存或付费率。评论提到“崩溃”应记录为用户报告，未经实测不能升级成已复现故障。只做采集时不输出“一致性好/差”“最重要需求”等分析结论。

### C02 商店资料采集

**目标：**记录竞品对外表达的定位、功能卖点与展示方式，和实机观察进行对照。

| 项目 | 约定 |
|---|---|
| 输入 | 指定 App 链接或 ID、平台、商店国家/语言、采集日期及需要的字段；可选关键词搜索候选 |
| 输出 | App 元数据、标题/长短描述、商店截图原图、页面来源快照、字段缺口；若做发现，另交候选清单 |
| 处理思路 | ①定位正确 App；②记录商店环境和页面时间；③采集公开文案、元数据及图片；④保留原文、图片顺序与获取地址；⑤派生译文或缩略图；⑥标记缺失、访问失败和页面更新 |
| 上下游 | 接任务单；送 C05；经 C06 后供定位、卖点、竞品差异及 F1 分析；与 C03 保持来源类型区分 |
| 资料不足时 | 地区不可见、页面下线或某字段不可读就保留缺口；不从其他国家页面静默补齐本市场资料 |
| 完成标准 | 名称、ID、平台一致；文案和截图能回查来源；宣传图片清楚标为“商店宣传图”；更新时保留历史快照 |

**边界：**商店截图和描述只证明公开展示了什么，不能证明当前安装版本具有同样页面、全部功能可用或效果属实。搜索候选只是候选，主对标/功能参考/商业化参考的最终选用由产品负责人明确。

### C03 App 实机走查与截图

**目标：**用户给出 App 和范围后，围绕真实页面与操作记录可核对的体验路径，形成按模块阅读的证据包。

| 项目 | 约定 |
|---|---|
| 输入 | 已安装 App 的包名、选定设备、起始状态、模块/流程范围、停止条件；按需提供虚构测试数据和必要操作说明 |
| 输出 | 原始截图；可用时的 UI XML/控件信息；页面/状态清单；操作与跳转记录；模块流程 PNG；走查地图；已覆盖、未覆盖及暂停原因 |
| 处理思路 | ①确认设备、包名与版本；②读取当前 UI 并确认所在页；③截图和标记模块/页面/状态；④基于当前可见控件执行下一步；⑤再次读取 UI 和截图，记录实际结果；⑥维护已走查路径与待探索分支；⑦按证据拼接模块流程图并汇总缺口 |
| 上下游 | 接任务单；送 C05；经 C06 后供竞品流程、商业化触点、页面状态和体验问题分析；外部构建实测也可沿用此证据格式 |
| 资料不足时 | 设备断开、页面变化、控件失效、登录/购买/系统操作等超出范围时暂停；保留已完成证据和恢复位置；操作未执行或结果未读回就不画确定跳转 |
| 完成标准 | 每个流程节点有对应原图；每条确定跳转能追溯到实际动作和结果；实际覆盖与指定范围可对照；未走到的分支标明；拼图内容可回到单张截图 |

恢复前重新确认设备、App、版本及当前页面；已发出但结果未知的动作先标记不确定，重新观察后再决定下一步，不能直接重复上一动作。若版本或环境已经变化，保留旧会话并标明新的条件。

**三种可复用入口需要区分：**

| 入口 | 谁判断下一步 | 适用方式 | 主要依赖与限制 |
|---|---|---|---|
| 人工操作的独立采集器 | 人 | 人选择 App、控件和状态，工具负责执行、截图与归档 | Android/ADB/设备；无需模型；人工步骤不能自动补成已执行路径 |
| 截图 Skill | 使用 Skill 的 Agent | Agent 按“观察当前页 → 截图 → 操作 → 读回”协议走查 | Skill 指令、脚本与 Agent 可用工具；移交其他 Agent 时需适配工具入口 |
| 工作台自动走查 | 独立 runner 中的模型 | 用户给包名和范围，模型在受限工具内逐步探索 | 当前实现依赖 Codex、模型、ADB 和设备；需要预算、暂停与恢复机制 |

三种入口应交出相同含义的证据，是否独立成一个工具由实现同事决定。自动探索允许在预算或停止条件处交付“部分覆盖”，不能承诺无人值守穷尽全部 App。截图只能证明当时界面；真实支付、广告收益、埋点入库或多设备稳定性需要对应测试证据。

### C04 外部数据整理

**目标：**承接留存、画像、下载、收入、投放等资料，让分析知道数据能支持什么、哪些不能比较。

| 项目 | 约定 |
|---|---|
| 输入 | 用户提供的文件、报表、链接或明确授权的数据源；研究问题、指标、平台、地区、周期和对象 |
| 输出 | 原始数据/快照、字段与指标口径表、标准化数据表、质量与覆盖说明、可比较/不可比较项、缺口 |
| 处理思路 | ①定位数据源与覆盖范围；②核对对象、时间、国家、渠道、平台及指标定义；③区分实际观测、第三方估算和人工记录；④统一可安全统一的格式与单位；⑤只在同口径下比较；⑥标明数据无法支持的判断 |
| 上下游 | 接任务单及已提供资料；送 C05；经 C06 后供 F1、商业化分析及版本复盘；缺失不阻断评论与实机整理 |
| 资料不足时 | 没有数据源、权限、定义或必要分母时列缺口；仍可交其他已有证据，不编造数值、不根据截图推算经营结果 |
| 完成标准 | 每个数字能回查来源和周期；读者知道分子/分母、样本/覆盖、实际值或估计值；不能比较的数值被明确隔开 |

**指标最少保留以下口径：**

| 数据 | 必须附带的说明 |
|---|---|
| 留存 | cohort 定义、起始事件、回访事件、D1/D7 等计算口径、时区、时间范围、分子分母、版本/地区/渠道及筛选条件 |
| 画像 | 数据来源、样本/覆盖、时间与分类方法；区分直接统计、抽样、模型推断和评论中的自述 |
| 下载 | 新增下载/安装/首次打开等具体定义、统计周期、地区、平台及实际/估算属性 |
| 收入 | 广告/IAP/付费下载/合计、税费及平台分成前后、币种、周期、地区、实际/估算属性及覆盖范围 |
| 投放与回收（仅本轮明确涉及时） | 花费、归因规则、cohort、用户指定的收入窗口、毛/净口径与数据成熟情况；需要计算回收效果时明确公式和收入构成 |

不同地区、周期、cohort、币种或收入构成不能直接相加/比较；确需换算或聚合时保留原值、计算步骤及来源。只有 IAP 的估算不得标成广告加 IAP 总收入；没有收入或花费资料就不能给真实回本结论。用户选定的观察窗口之外，后续价值、订阅回收与长期留存若未覆盖，应明确留作判断盲区。本工作台不预设统一的收益指标或固定回收周期。

首版建议支持资料导入与人工标注。自动连接哪些数据服务，应在来源、可用字段和业务需求明确后再做；本文不假定已接入任何经营数据平台。

## 5. C05 标准化与去噪

**目标：**把异构资料整理为下游可检索、可引用、可复核的记录，保留原始证据及不同环境的差异。

| 项目 | 约定 |
|---|---|
| 输入 | C01—C04 原始资料包，以及已有文档、评审意见、原型快照与实测材料 |
| 输出 | 标准化记录、原始证据索引、重复/合并映射、解析及翻译结果、覆盖与质量报告、待处理冲突 |
| 上下游 | 承接所有来源；输出给 C06；需补采时只把具体缺口回传对应来源能力 |
| 完成标准 | 任一派生内容能回查原始材料和处理方式；相同资料重复导入不会产生难以解释的重复；不同环境/版本记录不会被误合并；缺失与解析失败可见 |

**处理顺序：**

1. **先保留原件。**为来源建立稳定编号，保存原文件/快照及获取记录；解析失败仍能查看原始文件。
2. **再整理字段。**区分商店图、实机图、评论、指标、需求、评审、实测；统一日期/编码/字段名称，原值保留。扫描 PDF 无文字时标明需要 OCR，不能交空文本并称解析成功。
3. **按类型去重。**文件可按内容摘要识别精确重复，评论可按 ID/内容识别重复；近似文字、相似截图只作待核对候选。相同文案出现在不同国家、版本或页面时保留各自上下文。
4. **派生处理分列。**翻译、摘要、标签和图像拼接保留处理关系；不覆盖原文。异常值、少数负面评论或失败分支不能仅因“不常见”而删除。
5. **整理观察与覆盖。**把“材料里直接有什么”写成可核对观察；把解释放入判断类型；记录本轮已读与未读、成功与失败、选样限制和冲突。
6. **产出可用索引。**提供稳定引用及必要的搜索文本，按项目、对象、版本和来源筛选；大文件可分块，但每块都能定位回原件。

**衔接要求：**C05 不负责决定我方产品最终做什么。发现冲突时同时交出冲突内容、各自条件和来源，不以“模型认为更可信”静默删除其中一方。去噪不等于筛掉不利于预设结论的材料。

## 6. C06 SSOT：当前依据与产品基线

SSOT（Single Source of Truth）在这里指**项目当前采用依据的统一入口**，包括证据、判断、确认规则及其关系。它可以由资料索引、结构化记录和已确认文档组成；检索到一段内容不等于它自动成为当前事实。

### 6.1 三层内容

| 层 | 存什么 | 谁可以怎样使用 |
|---|---|---|
| 证据与观察 | 来源索引、原文/原图/数据定位、实际观察、环境与覆盖 | 支持复核“看到了什么”；保留时间与条件，不自动扩大适用范围 |
| 分析与建议 | 有依据的解释、竞品判断、机会、我方方案建议、反证与待验证项 | 可供讨论；明确推断身份，不自动覆盖事实或规则 |
| 当前确认基线 | 已采用定位/范围、公共规则、页面/状态、已确认产物版本、决定与待同步项 | 作为本轮设计、PRD、埋点和验收预期的依据 |

### 6.2 输入、处理和输出

| 项目 | 约定 |
|---|---|
| 输入 | C05 标准化记录；C07/C08 的确认稿；产品负责人明确决定；已有指定基线；变更与外部同步证据 |
| 处理思路 | ①按项目/版本/对象组织；②分别存证据、判断和决定；③关联来源及依赖；④固定本轮采用快照；⑤记录确认人、时间、适用范围；⑥更新时保留旧版本并列受影响产物 |
| 输出 | 当前基线及版本号、已确认规则/范围、证据与判断索引、待决定冲突、已知缺口、变更及待同步清单；供任务读取的资料快照 |
| 上下游 | 接 C05 和已确认产出；供 C07/C08；新证据回到 C05，基线变更进入 C08 影响检查 |
| 完成标准 | 能回答当前采用哪版、依据是什么、谁何时确认、适用于哪里、哪些仍是草稿、哪些外部对象尚未同步；历史结果可用旧快照复查 |

### 6.3 冲突怎么处理

**我方应如何做**，优先采用当前产品负责人明确确认及其指定基线；没有新决定时沿用已有已确认规则。当前原型/App 表现描述实际情况，历史记录和模板提供参考。

**实际已经怎样**，必须回到对应文件、画面或实测证据。用户确认了一条新规则，只能改变约定，不能覆盖“旧 App 仍显示旧规则”的观察。反过来，App 实现偏差也不能自动改写已确认需求。

处理一个冲突时应同时记录：冲突双方、来源/版本/时间、适用条件、当前采用规则、实际偏差、需要谁决定或同步。不能按文件名“最终版”、最近上传时间或检索排名静默裁决。

公共规则沿用 RULE 编号，只维护一份规则正文；页面说明引用规则，并补本页触发、表现与例外。跨产物变更沿用同一 REV 记录，不在每份文档另建一张彼此冲突的同步表。

### 6.4 上游更新后的衔接

**新增、纠正或失效证据 → 保留新旧快照和状态 → 标记受影响判断/产物 → 复核是否需要改变方案。**

- 不改变方案：记录复核依据与结论，继续沿用原规则；本轮引用需要调整时仍修正来源。
- 需要改变方案：确认新决定 → 更新受影响规则/正文 → 同步外部对象 → C08 复核。

新证据和新模型输出不自动替换已确认基线。对仍使用旧基线的交付物显示“依据已变化，需复核”，保留其原确认记录和旧内容；复核后可继续沿用，也可形成新修订。已经输出修订文字但没有实际写入 Figma/Axure 等对象时，状态保持待同步。

方法、模板、过往案例可从 Product KB 检索。它们属于参考资料，与当前项目事实分开；本轮产物不默认回写全局知识库或外部知识库。

## 7. C07 分析与产品方案产出

**目标：**基于本轮选用证据与当前基线，完成指定产品工作，而不是每次重做整套研究。

| 项目 | 约定 |
|---|---|
| 共用输入 | 本轮问题与范围、C06 当前基线、明确选用的来源快照、相关原型/文档/评审意见；可选方法与案例 |
| 共用处理 | ①检查输入与覆盖；②提取相关事实；③区分观察、判断、建议和确认规则；④按任务模板组织；⑤引用底层来源；⑥输出差异、缺口与本轮停止位置 |
| 共用输出 | 指定类型草稿、实际使用的资料索引、采用基线、待决定项及外部待同步位置 |
| 上下游 | 从 C06 取输入；草稿送 C08；确认部分回到 C06；需要补证据时回传明确问题到 C01—C04 |
| 完成标准 | 结论可回查证据；方案不冒充既有事实；当前产品的价格/广告/权益值不从模板照搬；本轮范围与缺口明确；稳定编号可被下一任务沿用 |

### 7.1 可独立调用的下游任务

“必要输入”指形成对应结论所需的材料；材料缺失时，可交有标注的部分稿或待补项，不能补造成完整稿。以下任务按需组合，不要求全部执行。

| 编号 / 任务 | 必要输入；可选输入 | 处理思路 | 输出 | 衔接 |
|---|---|---|---|---|
| D01 评论分析 | 评论样本、筛选/取样口径；可选实机证据 | 按用户任务、问题、诉求归类，回引原话，区分频次与严重度 | 主题、代表评论、样本内统计、判断与限制 | → D02/D03；不能单独定需求优先级 |
| D02 竞品分析 | 明确研究对象/参考用途及本轮实际资料；可选 D01、外部数据 | 按“具体观察 → 产品判断 → 我方取舍”比较功能、流程与商业化 | 有证据的差异、可借鉴点、不采用点、缺口 | → D03、D05、D07；局部资料就交局部结论 |
| D03 F1 新品需求分析 | 项目方向与限制、品类用户资料、竞品候选/选用资料；各章采用前章确认内容 | 品类与用户 → 竞品差异 → 定位与范围 → 功能框架与核心模块 → 流程、商业化与交接 | 5 组章节确认稿及合并 F1；首次/再次使用、V0 取舍、商业化方案 | → D06/D07；按需 D09；不强制完整 F2 |
| D04 现有产品基线 | 当前线上资料/实际观察及已确认约定；可选历史版本结论 | 分别整理实际功能/流程/商业化与应有规则，列已知偏差 | 可追溯的当前产品基线 | → D05；当前材料未覆盖部分不补写 |
| D05 版本简报 | D04 或指定现有基线、本次目标与变化 | 说明当前行为、目标、增量变化、保持范围及影响模块 | 本版做什么、为何做、做到哪里及成功口径 | → D06/D07/D09；无需重做 F1 |
| D06 公共规则 | 已确认范围/变更与跨页面约定 | 收拢权益、广告、导航、数据等共享逻辑，沿用 RULE ID | 规则、触发/失效条件、例外与涉及页面 | → D07—D13；仅有局部规则时不强建规则库 |
| D07 功能流程与页面状态 | D03/D05 中的确认范围及相关规则 | 先写用户任务流程，再拆入口、动作、结果、失败/取消/恢复及页面状态 | 分模块流程、页面/状态清单、规则引用 | → D08/D09/D11/D12 |
| D08 原型与需求旁注交接 | D07、相关规则、指定视觉/原型参考 | 按页描述内容、控件、状态、交互和中文旁注，标出外部制作位置 | 可交 Figma/Axure 制作的逐页说明与待同步清单 | 外部制作后回读快照 → C05/C08；文档生成不代表原型已画好 |
| D09 F2 核心 PRD | 本轮范围、当前页面/旁注/规则；缺少原型时注明依据 | 按实际模块展开行为、业务规则、状态、例外/恢复及验收预期 | 研发可执行的核心 PRD，沿用页面/状态/RULE ID | → D11/D12/D13；与页面说明复用正文口径 |

| D12 产品验收用例 | 确认 PRD/页面/规则、实际验收范围 | 以产品场景写操作和预期，覆盖本轮核心及必要异常 | 按模块的“验收场景｜操作步骤｜预期结果”三列表，保留稳定用例 ID | → D13；只描述预期，不填写通过结论 |
| D13 F3 开发验收记录 | D12/PRD 预期；填写实测另需构建、环境及真实测试材料 | 在同一用例下追加实际、状态、证据、问题与复测 | 未测计划或有证据的实测记录，二者明确区分 | 问题 → D10/D05；无实测材料默认 NOT_RUN |
| D14 版本结果与复盘 | 版本目标/变化、实际发布范围、对应数据与反馈；可选实测/投放材料 | 按相同口径对照目标与结果，区分相关性和因果，说明数据成熟度 | 本轮结果、依据、局限、继续/调整/停止建议 | → D04/D05；无经营数据就不交回本结论 |

F1 的章节稿依序确认；最终合并只统一编排和来源编号，不调用模型重写已确认正文。分析中提出的新定位、商业化或范围建议，须保持“建议/待确认”身份，明确决定后再进入基线。

### 7.2 四种常用组合

| 场景 | 推荐路径 | 本轮停止位置 |
|---|---|---|
| 新品定义 | 指定竞品与资料 → C01—C06 → D03 → D06/D07 → 逐模块 D08 → C08 | 交付当前原型说明和规则；需要研发细节时补 D09/D11/D12 |
| 版本迭代 | 已有基线或 D04 → D05 → 相关 D06/D07/D08/D09 → C08 | 只交本版增量、影响与待同步；D11/D13 按需 |
| 单次竞品研究 | 指定问题与参考对象 → 所需 C01—C04 → C05/C06 → D01/D02 | 交研究结论及证据，不自动衍生完整产品方案 |
| 版本复盘 | 版本目标与实际变化 + 对应数据/反馈 → C04/C05/C06 → D14 | 交有依据的后续建议；确认后进入下一版 |

流程可以从已有的确认成果继续。阶段入口是任务组合，不能把“新品开发”“版本迭代”再拆成与底层任务重复的独立能力。

## 8. C08 一致性与交付检查

**目标：**检查同一个产品约定在规则、流程、页面、旁注、PRD、埋点和验收预期之间是否一致，形成能落实的修订与交接清单。

| 项目 | 约定 |
|---|---|
| 输入 | 本轮基线及变更、实际提供的各类稿件/原型快照、真实评审意见、页面/状态/规则等引用 |
| 处理思路 | ①列明读取了哪些材料/位置；②检查引用与编号；③对照范围、路径、规则、数值、文案和状态；④检查改动涉及哪些产物；⑤输出定位及最小修订；⑥修订后回查旧口径残留 |
| 输出 | 可定位差异、遗漏、冲突、建议处理及依据；同一 REV 下的影响/修订/同步结果；未读、未决定、未写回和未测试项 |
| 上下游 | 接 C06 基线与 C07 草稿；普通修订回对应任务；需要改变产品决定的差异回产品负责人；确认结果回 C06 |
| 完成标准 | 每项问题能定位并知道改哪里；修订结论有实际改动/核对依据；所有未闭合项随交付保留，不将缺失材料写成“检查通过” |

**检查重点：**

- 版本范围、已后置内容是否被旧文档重新带回。
- 同一 RULE 的额度、时机、权益、成功/失败条件是否一致；页面是否只引用一份规则正文。
- 页面、状态与流程是否有入口、结果及必要返回/恢复；图中的路径是否有证据或明确的设计身份。
- PRD、旁注、埋点和验收预期是否引用同一页面/状态/规则，改名后是否遗漏关联位置。
- 来源是否真正支持结论；用户报告、推断、建议与真实观察是否混写。
- 已确认新规则是否仍未写入外部原型；是否把文档审查写成真机测试或商业效果证明。

**单项问题至少包含：**问题 ID、冲突/缺口、双方位置、适用基线、影响、建议修订、决定或修订情况、待同步/未核对项。无需另起一套庞大评审流程。

**任务：**研究“从系统文件选择器取消导入后如何返回”，给我方 V0 输出这一模块的原型说明、埋点和产品验收用例；不研究全 App。

| 产出 | 具体内容 |

## 10. 同事实现后应达到的交接效果

以下是产品行为验收场景，用来对齐预期，不代表当前系统已经全部通过。

| 场景 | 操作/输入 | 预期结果 |
|---|---|---|
| 局部资料也能开展工作 | 只提供评论与实机截图，没有留存/收入 | 能交覆盖范围内分析；明确数据缺口，不补写用户比例、留存或回本结论 |
| 来源身份不混 | 同时提供商店宣传图和真实截图 | 两类图分别标识；分析可对照，但不能互相冒充 |
| 重复导入可解释 | 同一 CSV 再导入；另有不同市场的相同评论文本 | 精确重复可识别并保留导入关系；不同上下文不被静默丢弃 |
| 部分走查失败可恢复 | 指定三个模块，第二模块出现范围外登录 | 保存已完成证据、暂停点与未覆盖项；恢复或重试不伪造已走路径 |
| 判断与决定有边界 | 模型提出一条广告时机建议 | 草稿保持建议身份；明确确认后才成为我方当前规则 |
| 新规则不掩盖实际偏差 | 规则已改，外部原型/旧 App 仍是旧行为 | 当前规则和实际观察同时可见；列出待同步与差异，不显示全部完成 |
| 变更可以传递 | 一条跨页面规则更新 | 形成可定位的影响清单，相关产物能用旧基线复查，新稿只改受影响内容 |
| 指标口径不兼容 | 一份只有 IAP，另一份为广告加 IAP；周期也不同 | 不直接比较总收入或计算统一 ROI；说明差异及补齐条件 |
| 预期不冒充测试 | 只有 PRD 和验收用例，没有构建/实测 | 交产品验收预期；F3 保持 NOT_RUN，不生成通过或失败结论 |
| 局部审查不冒充全量 | 只提供两个页面节选 | C08 写明读取范围，仅判断已覆盖位置，其他内容保持未核对 |

## 12. 建议落地顺序与职责

### 12.1 先做什么

| 优先级 | 建议内容 | 先做的原因 |
|---|---|---|
| P0 | 对齐第 3 节字段和状态；复用 C01—C03；实现 C05 原件/标准记录/来源索引；C06 先支持当前基线与人工确认；C07 先跑竞品分析或一个模块需求；C08 能指出并跟踪差异 | 先打通一条“证据 → 规则 → 交付”链路；任何下游产物都可解释依据，减少重复录入与口径返工 |
| P1 | 用同一数据约定接齐常用 D01—D14；支持基线变更影响、修订版本、部分失败重试；按实际需要接外部原型快照 | 验证共用约定能服务新品和迭代，避免每个任务各造一套数据 |
| P2 | 根据明确数据源和业务价值接入 C04 自动同步；再优化相似去重、观察归并与自动走查覆盖 | 数据源和业务问题明确后再投入，避免做出无法用于判断的“自动化” |

共享的项目/版本、原件存储、来源索引、任务状态、模型调用、版本/批注、导入导出与检查应尽量复用。每项能力拥有自己的业务输入/输出和处理规则即可，不必把每个按钮做成 Skill，也不必一开始拆成多个服务。

### 12.2 双方各自提供什么

| 产品侧提供 | 落地同事负责 |
|---|---|
| 研究目标、选用竞品及用途、本轮范围和停止条件 | 对象定位、采集/处理、结果归档与可恢复执行 |
| 可提供的数据来源、指标定义与资料使用范围 | 字段映射、质量检查、来源关联与缺口呈现 |
| 定位、范围、价格/广告/权益等业务决定；明确采用哪个基线 | 正确存储决定与版本，不用模型猜测替代业务确认 |
| 对输出的产品判断与确认 | 依据快照、草稿生成、检查、修订与影响跟踪 |
| 外部原型/测试/发布等工作的实际交接人和范围 | 在授权范围内接入或交接，真实记录待同步/已执行/已核对 |

首轮可直接用第 9 节同等范围的真实模块验收链路。接入具体经营数据平台、增加外部自动写入、扩大自动走查范围时，再补对应输入、输出、权限与验证范围；这些增强不应阻碍基础资料与需求链路先可用。

**本说明的交接终点：**同事能够据此拆出八组能力，明确每组收到什么、如何处理、交出什么、下一步由谁使用，并能解释任何交付物的来源、当前规则和未完成事项。具体技术方案、排期和实现由落地同事制定。
