# GBA Emulator 全流程运行审计

> **历史审计说明：** 本文保留当时的运行证据，不代表当前默认流程。文中提到的 Fast F1–F6、技术 Spike 和条件闭环已被 V0.3 三件套替代；当前用法请以 `WORKFLOW-USER-MANUAL.md` 为准。

## 1. 审计结论

这套流程可以生成完整的新品分析、产品框架、页面级 PRD 和验收方案，但当前默认形态更像“中大型团队的完整立项流程”，不完全适合小团队快速迭代。

本次实际运行后的建议不是删除方法论，而是增加一条 **Fast Iteration Path（快速迭代路径）**：

```text
已决定要做的品类
  → 快速定义卡（1–2 天）
  → 技术 Spike + 竞品评论证据并行（1–5 天）
  → Android MVP 闭环（导入/启动/保存/恢复）
  → 核心页面 PRD + 最小验收
  → 内部测试
  → 再补完整研究、商业化和跨平台规划
```

机会门不应阻断流程，因为你已经明确“输入的新品就是要做的”。但许可证、核心可用性、存档可靠性和明显合规风险仍然是硬阻塞，不能因为跳过机会门而跳过。

本次没有修改原始 GBA 项目结论，也没有把资料写入正式 Product KB 或上传 GitHub；本文件和修改清单是本地审计产物。

### 当前最终判断

- 可以进入 Android-first V0 的小规模开发和技术联调。
- 可以并行准备内部测试。
- 不能宣称 V0 已通过，也不能进入完整外部发布准备。
- 进入内部测试前必须关闭：core/许可证、支持格式、存档可靠性、进程被杀恢复、文件重新授权、设备与手柄范围、合规文案和硬阻塞 QA。
- 目标用户尚未完整定义不会阻断已经决定要做的品类，但会影响后续定位、文案和商业化判断。

## 3. 各阶段发现的内容漏洞

### 3.1 T1 新品需求分析

已补齐：

- 品类已决定，因此没有重新设置机会门；
- Android-first、GBA-only、本地文件、可靠存档的 V0 范围；
- 竞品“借鉴机制 / 参考体验 / 不复制资产”的边界；
- 用户价值、核心闭环、风险、Kill Criteria 和技术 Spike；
- 事实、推断、假设、决策、风险、待验证的区分。

仍暴露的问题：

- T1 默认一次性展开市场、用户、竞品、政策、商业化和指标，进入可运行验证太晚；
- 全球五区域和多竞品卡片对小团队早期决策价值有限；
- 10–15 名访谈、20 个测试 ROM、5 类设备等数字容易被误认为当前必须马上完成；
- 历史资料中的价格、下载量、评分和指标目标，虽然已标注待验证，但模板仍容易让读者当成事实；
- 合规部分指出“需要确认”，但没有直接绑定 Owner、截止时间、书面结论和阻塞规则；
- 技术 Spike 应更早与 T1 并行，而不是等完整 T1 写完；
- 目标用户未知时，T1 仍然花费过多篇幅进行画像推断。

### 3.2 T2 产品框架与版本规划

已补齐：

- S-01 core 与许可证；
- S-02 文件导入与生命周期；
- S-03 存档可靠性；
- S-04 设备与输入；
- S-05 可用性；
- S-06 验收样本；
- 每个 Spike 都有输入、输出、完成条件和阻塞判断；
- V0 只保留 Android/GBA/本地文件/触控与基础手柄/本地存档。

仍暴露的问题：

- 条件虽然被列出，但原模板没有强制 Owner、截止时间、证据链接和下一次复核时间；
- T2 仍可能被理解为“先完整规划，再开发”，没有把 Spike、评论证据和低保真交互正式设为并行；
- 竞品研究虽增加了“借鉴/参考/不复制”，但没有独立的结构化交付物；
- 对小团队来说，T2 的版本规划应先服务于 1–2 周验证，而不是提前规划大量后续版本；
- 设计可以开始什么、研发必须等待什么，虽然有说明，但没有统一的交接状态字段。

### 3.3 T3 页面级 PRD 与原型交接

已补齐：

- 首次导入、首页、详情、游戏会话、暂停/保存、恢复异常、重新授权、设置与帮助；
- Loading、Empty、Error、Timeout、Permission Denied、Offline、Interruption、Restore、Success；
- 存档冲突、进程被杀、文件移动和手柄断连的恢复路径；
- 产品规则与技术 Spike 规则分开；
- 页面与原型节点、验收路径的映射。

仍暴露的问题：

- 默认 8 个页面和全状态矩阵对快速验证偏重，第一轮其实只需要核心 4 个页面加异常矩阵；
- 工作台只生成 PRD 文档，没有真实原型文件或原型工具交接链接；
- “可以给设计”与“可以给研发”已经写出来，但没有转成机器可追踪的交接清单；
- T3 依赖 T2 已接受，实际开发中应允许基于“已接受部分 + 明确警告”的草稿并行推进；
- 兼容性、存档和文件授权规则仍停留在产品描述，必须明确哪些字段只能由 Spike 冻结。

### 3.4 T4 埋点与验收

已补齐：

- 8 个最小事件：导入、启动、会话、保存、恢复、重新授权、核心闭环，以及辅助的导入开始；
- 24 条 QA 场景，覆盖主流程、异常、设备、手柄、合规和埋点最小化；
- 硬阻塞、必须修复、可后置三层门槛；
- 1–2 周内 Spike、开发、QA 和联调并行顺序；
- 明确“计划不是实际通过”，没有真实构建和测试证据不能标记通过。

仍暴露的问题：

- 原模板把“计划型 T4”和“真实构建验收型 T4”混在一起；
- 原模板有 iOS、付费、广告等泛化字段，在 Android V0 中会造成无效填写；
- 真实结果、设备、构建版本、录像、日志、Owner 和复测证据不是强制结构；
- 小团队第一轮不需要完整行为分析，应默认 5–8 个闭环事件，其他事件后置；
- “Conditional” 如果没有截止日期和责任人，可能长期悬置。

## 4. 与日常工作方式的匹配度

| 日常工作特征 | 当前流程表现 | 判断 |
|---|---|---|
| 品类输入就是要做 | 已支持跳过机会门 | 匹配 |
| 快速迭代 | 默认 T1–T4 串行且内容较重 | 不匹配，需要 Fast Path |
| 小团队 | 默认要求多区域、多访谈、多设备、多种交付 | 不匹配，需要分层门槛 |
| 竞品对标开发 | 有竞品研究，但缺少独立 Delta Pack | 部分匹配 |
| Android-first | T2–T4 已能收窄 | 匹配，但模板仍有 iOS 泛化字段 |
| 先做可运行闭环 | 当前 T1 之后才进入 Spike | 不匹配，应把 Spike 前移并行 |
| 允许先做再补研究 | 依赖前一阶段 accepted，偏线性 | 不匹配，应允许 draft with warning |
| 交付物直接可用 | 文档较完整 | 匹配；但真实原型和构建证据仍需外部工具 |
| 不做投放/商店发布 | 本次全程已排除 | 匹配 |

## 5. 本次未能通过文档闭合的 GBA 内容缺口

这些不是工作流设计问题，而是项目本身需要补充的输入：

1. emulator core 和许可证的书面结论；
2. 合法测试文件的来源和可说明性；
3. 第一版支持的文件格式，建议先冻结 `.gba`；
4. 游戏内存档、Save State、自动备份和冲突处理模型；
5. Android 设备矩阵和最低兼容范围；
6. Bluetooth/USB 手柄样本和映射规则；
7. 文件移动、撤权后的指纹/匹配策略；
8. 真实用户对“导入—保存—恢复”任务的可用性证据；
9. 目标用户、首发地区、价格和商业化证据。

其中 1–7 是进入内部测试前的硬条件；8 是高优先级验证；9 不阻断 Android V0 技术闭环。

## 6. 运行过程中暴露的系统性漏洞

- **内容过重**：完整模板把“现在需要决定”和“以后有价值”放在同一层。
- **流程过线性**：文档、Spike、竞品评论和 QA 设计没有形成正式并行路径。
- **条件不可关闭**：缺少统一的 Owner、截止时间、证据、状态和复核日期。
- **证据层级不够强制**：历史资料、实时事实、规划目标和实测结果容易混在一起。
- **竞品工作不够产品化**：没有把评论采集、原始样本、痛点聚类、借鉴边界做成标准交付物。
- **交接不够真实**：PRD 可以生成，但原型、构建、测试证据仍需人工转接。
- **T4 过早完整化**：埋点和 QA 容易先做成大表，而不是围绕核心闭环的最小验证。
- **技能与工作台存在漂移风险**：当前 `overseas-consumer-app-lifecycle` 技能文本仍保留完整新品/机会门导向，而工作台和本次要求已转为“品类已决定、机会门可跳过”。需要统一。

## 7. 建议的目标形态

### 快速路径（默认）

1. **输入卡**：品名、平台、竞品参考、必须对标的核心能力、已知硬约束、期望验证周期。
2. **快速定义卡**：目标场景假设、竞品 Delta、V0 闭环、明确不做、三项最大风险。
3. **并行 Spike 包**：只拆会阻断开发的技术与合规问题，每个问题有 Owner、截止时间、输出和证据。
4. **核心交互包**：核心 4 页面 + 异常状态矩阵；8 页面版本按需要生成。
5. **最小 T4**：5–8 个事件、核心 QA、设备/构建/录像/日志证据。
6. **内部测试结论**：Go / Conditional / Hold，以及条件关闭清单。

### 完整路径（按需触发）

当产品要扩大地区、做商业化、做双端、做正式发布或需要跨团队协作时，再展开完整 T1、完整竞品卡、完整用户研究、完整指标和完整 T4。
