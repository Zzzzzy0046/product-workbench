## 2. Heart Rate 还贡献了一套“产品需求展开模板”

Heart Rate 的 Axure 需求不是一份普通页面原型，而是一个完整需求包。

### 2.1 产品信息层

```text
产品信息
├── 版本信息
├── 竞品截图
├── 需求框架
└── 产品流程
```

这一层回答：

- 当前版本做什么；
- 为什么这么做；
- 产品有哪些模块；
- 用户如何完成核心任务；
- 哪些页面和状态属于当前版本。

### 2.2 页面需求层

```text
需求详情
├── 启动流程
├── 主页
├── 心率测量页面
├── 推送通知管理页面
├── 趋势页面
├── 数据洞察页面
├── 设置页面
└── 订阅页
```

这些页面需求已经包含大量研发可执行字段：

- 页面说明和进入条件；
- 展示字段、默认值和计算公式；
- 按钮和页面跳转；
- 权限、Apple Health、订阅资格等状态；
- 数据为空、部分缺失、删除联动、日期范围、导出失败等边界；
- English UI Copy 和中文需求说明并存；
- `需要美术出图` 等设计交接标记。

因此，Heart Rate 模板应被识别为两个独立层次：

1. **新品为什么值得做、做什么**：新品分析文档。
2. **这个版本每个页面怎么工作**：Axure 页面需求包。

二者不能合成一份无限长的文档，也不能只保留其中之一。

## 3. 模板演进判断

| 版本 | 优点 | 缺点 | 应保留内容 |
|---|---|---|---|
| Heart 新品模板 | 产品故事完整、判断鲜明、适合上会 | 平台、指标和证据状态不够标准化 | 结论先行、章节叙述、功能框架→详述→流程 |
| Printer 模板 | 商业化、政策、信任、版本优先级更强 | 用户证据和跨平台拆分仍不够系统 | 政策/信任独立检查、P0/P1/P2/No |
| PDF Reader Heart 模板版 | 成功把 Heart 写法迁移到新产品 | 仍偏 Android 单侧，指标体系相对薄 | 方向判断、边界、预研、最终取舍 |
| Doc Reader 0–12 模板 | 证据、平台、MVP、指标和决策最完整 | 容易写成表格堆积，叙述感变弱 | 作为当前标准骨架 |
| Heart Axure 需求包 | 页面、状态、数据规则和商业化交接很具体 | 不适合承担市场与立项分析 | 作为方案确认后的需求展开模板 |

最终不是选择其中一个，而是组合：

> **用 Doc Reader 0–12 章模板保证完整性，用 Heart 的写法保证判断质量，用 Printer 的政策/商业化检查增强工具类项目，用 Heart Axure 结构承接页面级交付。**

## 4. 推荐的四层模板体系

### T1：新品需求分析

适用：只有方向、需要判断是否立项。

必须回答：

1. 市场和用户问题是否成立？
2. 首个 Beachhead 用户和场景是什么？
3. 用户为什么下载、回来、付费？
4. 竞品没有解决什么？
5. MVP 只验证什么？
6. Android/iOS 分别是否 Go？
7. 最大风险和停止条件是什么？

模板：当前 0–12 章结构，使用 Heart 风格写法。

### T2：产品框架与版本方案

适用：方向已通过，需要定义这个版本做什么。

内容：

- 版本信息；
- 一句话定位与产品原则；
- 功能框架；
- 用户主流程；
- P0/P1/P2/No；
- 商业化、权限、平台差异；
- 预研与依赖；
- 页面清单。

模板来源：Heart `需求框架/产品流程/版本信息` + Printer 版本优先级。

### T3：页面/功能 PRD 与原型标注

适用：进入设计和研发。

页面结构：

`页面说明 → 页面进入 → 页面模块 → 展示规则 → 交互说明 → 页面状态 → 数据规则 → 异常&边界 → Acceptance Criteria → 埋点`

模板来源：Heart Axure 页面需求、`prd-prototype-standard`、`prototype-requirement-writer`。

### T4：测量、测试与验收

适用：开发交付、提测和上线。

内容：

- 埋点表；
- 测试用例；
- 功能验收状态；
- 设备/系统/版本信息；
- PASS/FAIL/BLOCKED/NOT_RUN；
- 失败证据和回归状态；
- 研发验收门禁。

模板来源：`tracking-spec-from-prototype`、`tracking-implementation-validator`、QA 流程。

## 5. 模板路由规则

| 用户请求 | 应使用的模板 | 不应直接使用 |
|---|---|---|
| “这个方向能不能做” | T1 精简评估版 | T3 页面 PRD |
| “写一份完整新品需求分析” | T1 完整版 | 只有功能清单的旧式文档 |
| “本期应该做哪些功能” | T2 | 直接画全量页面 |
| “按 Heart/Printer 那种结构写” | T1 + Heart 叙述风格 + 对应品类检查 | 机械照抄历史功能和价格 |
| “做这个页面/流程的需求” | T3 | 重写整份新品分析 |
| “根据原型生成埋点表” | T4 埋点设计 | `umeng-cli` |
| “检查实机是否埋上了” | T4 实机验收 | 用页面操作成功代替埋点 PASS |

## 6. 正式工作流应如何吸收这套模板

主控工作流需要新增一个 `template_router`：

1. 先判断当前处于 Idea、Discovery、Validation、Design、Build、Acceptance 哪个阶段。
2. 根据阶段选择 T1–T4，不让所有任务都套同一个长模板。
3. 每次读取当前项目已有模板，历史模板只提供结构和方法，不覆盖当前事实。
4. 同一个项目允许同时存在 T1、T2、T3、T4，但每层只有一个当前 Source of Truth。
5. T1 的产品决策必须能追踪到 T2；T2 的功能编号必须能追踪到 T3；T3 的关键动作必须能追踪到 T4。

推荐追踪关系：

```text
假设 A-01
  → 功能 F-03
    → 页面/状态 S-05
      → 验收 AC-05-02
        → 事件 EV-018
          → 测试 TC-044
```

这才是“完整工作流”：不只是阶段齐全，还要能从最初假设追踪到最终实机证据。

## 7. 最终建议

### 现在必须做

1. 把 T1–T4 模板路由纳入主控 Skill。
2. 将当前 0–12 章模板定义为 T1 标准骨架。
3. 将 Heart 的结论先行和章节叙述定义为写作标准，而不是另存一个互相竞争的模板。
4. 将 Heart Axure 的产品信息层和页面需求层纳入 T2/T3。
5. 给 T1–T4 增加统一编号和追踪规则。

### 可以后置

1. 找回原始 `新品Heart+Rate+.pdf` 后做逐页视觉复核。
2. 自动从 T1 生成 T2 骨架、从 T2 生成 T3 页面清单。
3. 自动检查功能、页面、AC、埋点和测试用例之间是否断链。

### 不要做

1. 不要把 Heart、Printer、Doc Reader 做成三套互相竞争的新品模板。
2. 不要为了保留历史模板而继承历史产品的用户、功能、定价或政策结论。
3. 不要把 Axure 页面需求当成前期市场和立项分析。
4. 不要把完整 0–12 章模板用于一句话或单页面小任务。

一句话总结：**Heart Rate 提供的是“怎么把新品讲清楚、怎么把页面写到能落地”的范式；当前工作流需要把它沉淀为 T1 新品分析 + T2 产品框架 + T3 页面 PRD，而不是只把它当成一个旧项目案例。**
