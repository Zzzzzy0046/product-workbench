# 新品需求分析方法

用户已经决定要做的品类，按当前阶段选择最小交付。日常主干为：

```text
市场与竞品分析 → 原型图＋需求说明 → 初审修改 → 终审整理 → 需求评审
```

F1 不是一张空洞定义卡，也不是正式立项报告。它沿用 Heart Rate 的产品故事结构：行业与市场、用户、竞品、定位、范围、产品框架、核心功能、主要流程、商业化和进入 PRD 的结论。竞品评论 CSV、政策来源、技术日志、截图和研究资料必须进入资料索引，并在对应产品结论中实际使用。

F1 保留五章分别生成与确认。竞品章可整理用户提供候选的下载、收入及体验资料，最终选用由用户决定；不是自动发现或自动选定竞品。近期下载与累计安装、商店收入与广告收入分开，保留平台、市场、周期、来源及未知项，不以缺值代替 0 或制造可比排名。结论采用“观察 → 对任务的意义 → 本产品借鉴、调整或不采用”的短条目。

结构要完整，但没有最低字数要求；最多按任务限制输出。资料不足的事实写明“当前资料未覆盖”，不要为了满足篇幅补写行业规模、用户比例、竞品功能、价格或商业化事实。背景只保留会改变产品方案的部分；竞品差异、产品范围、功能框架和模块级产品方案不能为了压缩篇幅而删除。

证据边界：用户在项目背景中明确写出的内容和当前项目上传/确认的资料，才可以支持当前产品事实；Product KB 中的历史案例、其他产品文档和商业化决定只用于理解结构与方法，不能迁移为当前项目结论。评论只代表采集样本，截图只描述看得见的内容，单一市场或单一竞品不得外推为全市场；这些边界在文中说一次即可。产品方案直接给出取舍，依赖假设的标明假设和推翻条件，不写成已验证事实。

快速模式不要求用户访谈，不使用事实/推断/假设/风险标签，不生成风险清单、技术 Spike、Gate、条件闭环、TAM/SAM/SOM 或五区域长表。技术问题直接进入 F2 的研发确认；真实问题进入 F3 的问题与复测表。

F1 不设置平台、权限、数据或政策章节，也不展开合规分析。具体页面确实依赖系统权限时，在 F2 对应页面写进入时机、拒绝处理和恢复路径。

F1 写到模块级产品方案，不硬凑用户分层、模块数、竞品数或标准 App 结构；同一场景不重复写成多种任务表达。第 6 章集中维护首版范围，交接章只引用范围和补充本轮下一步，不强制进入完整 F2。

原型旁注与 F2 共用一份已确认页面需求正文和稳定 ID。说明用途、呈现形式、区域位置层级、必要 UI 文案与操作结果；简单状态只补差异。已有旁注、流程索引和公共规则时沿用引用，只补本轮变化，不重新自由改写。F2 独立交接按需；产品验收保持“场景、步骤、预期”三列，F3 按需沿用原用例和事件 ID 增加实测、证据与复测，不另设计少量埋点或重写预期。

同轮变更只维护一份同步表，按“旧口径 → 已确认新口径 → 各产物具体位置”核对。未读取位置标未核对，未实际写回标待同步。该约束用于减少重复维护，不要求额外增加管理报告。

所有正式交付物默认中文，英文只保留必要技术名词和 UI copy。付费投放、媒体采买、投放归因、ASO 文案、商店素材和商店发布执行不进入本流程。

只有用户明确要求历史 0–12 章、正式投资评审或大型跨团队研究包时，才使用完整 T1–T4。
