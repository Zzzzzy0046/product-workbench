# 新品需求分析方法

用户已经决定要做的品类默认使用三份交付物：

```text
F1 新品需求分析 → F2 核心 PRD → F3 开发验收清单
```

F1 不是一张空洞定义卡，也不是正式立项报告。它沿用 Heart Rate 的产品故事结构：行业与市场、用户、竞品、定位、范围、产品框架、核心功能、主要流程、商业化和进入 PRD 的结论。竞品评论 CSV、政策来源、技术日志、截图和研究资料必须进入资料索引，并在对应产品结论中实际使用。

结构要完整，但没有最低字数要求；最多按任务限制输出。资料不足时写明“当前资料未覆盖，暂不下结论”，不要为了满足篇幅补写行业规模、用户比例、竞品功能、价格或商业化事实。背景只保留会改变产品方案的部分；竞品差异、产品范围、功能框架和模块级产品方案不能为了压缩篇幅而删除。

证据边界：用户在项目背景中明确写出的内容和当前项目上传/确认的资料，才可以支持当前产品事实；Product KB 中的历史案例、其他产品文档和商业化决定只用于理解结构与方法，不能迁移为当前项目结论。评论只代表采集样本，截图只描述看得见的内容，单一市场或单一竞品不得外推为全市场。产品方案可以提出建议，但必须使用“建议/本产品可/待确认”等方案措辞。

快速模式不要求用户访谈，不使用事实/推断/假设/风险标签，不生成风险清单、技术 Spike、Gate、条件闭环、TAM/SAM/SOM 或五区域长表。技术问题直接进入 F2 的研发确认；真实问题进入 F3 的问题与复测表。

F1 不设置平台、权限、数据或政策章节，也不展开合规分析。具体页面确实依赖系统权限时，在 F2 对应页面写进入时机、拒绝处理和恢复路径。

F1 写到模块级产品方案，F2 再写页面级结构、控件行为、业务规则、完整状态、恢复路径和验收，因此两份文档不会重复。F3 在同一份文档中持续更新计划与实测，引用日志、截图、录像和测试报告，不再拆成 Plan/Run。

所有正式交付物默认中文，英文只保留必要技术名词和 UI copy。付费投放、媒体采买、投放归因、ASO 文案、商店素材和商店发布执行不进入本流程。

只有用户明确要求历史 0–12 章、正式投资评审或大型跨团队研究包时，才使用完整 T1–T4。
